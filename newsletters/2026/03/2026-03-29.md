### **Interlock Ransomware Turned Cisco FMC Into a Zero-Day Weapon — Exploiting CVE-2026-20131 for 36 Days Before Cisco Knew**

The Cisco Secure Firewall Management Center (FMC) vulnerability CVE-2026-20131 (CVSS 10.0) is the headline story you need to act on today — literally today. CISA issued an emergency directive ordering all Federal Civilian Executive Branch agencies to patch or disconnect by Sunday, March 29. Amazon's MadPot global sensor network caught Interlock ransomware actively exploiting it starting January 26, 2026 — 36 days before Cisco published the advisory on March 4. The vulnerability stems from insecure deserialization of user-supplied Java byte streams in FMC's web management interface, allowing an unauthenticated attacker to execute arbitrary Java code as root. Amazon discovered the gap only because Interlock made an operational security blunder: they left their toolkit exposed on a misconfigured infrastructure server, giving Amazon Threat Intelligence an unintended look at the full multi-stage attack chain, reconnaissance scripts, and evasion techniques. Without that OPSEC error, the zero-day might have run longer.

Key findings:

- **CVSS 10.0 / Max severity** — unauthenticated RCE as root on Cisco Secure FMC via crafted HTTP request to the web management interface
- **January 26 exploitation start** — 36 days before the March 4 advisory; Interlock had a zero-day window while defenders had no IOCs
- **Active Interlock victims** — DaVita, Kettering Health, and multiple enterprise technology and software firms in the United States targeted during the zero-day window (per Zscaler ThreatLabz, targeting began March 6)
- **No workarounds available** — Cisco explicitly confirmed no workaround exists; patch is the only remediation path
- **CISA emergency directive** — Federal agencies must patch or disconnect today; non-federal organizations should treat this with equivalent urgency

> **"This wasn't just another vulnerability exploit; Interlock had a zero-day in their hands, giving them a week's head start to compromise organizations before defenders even knew to look."** — CJ Moses, CISO, Amazon Integrated Security

The FMC is a centralized control plane for Cisco firewall and security appliances — an attacker with root access to FMC effectively owns the entire security appliance stack it manages: firewall rules, URL filtering, IPS signatures, application controls. This is a blast-radius multiplier, not a single-device compromise. Interlock's toolkit, as exposed by the Amazon analysis, includes a PowerShell reconnaissance script for comprehensive Windows environment enumeration, browser artifact collection (Chrome, Edge, Firefox, IE, 360 browser), and active network connection mapping — a full pre-ransomware collection pass executed at scale.

**Immediate actions:**
- Apply Cisco FMC security updates **immediately** — today, regardless of change window procedures
- If patching is delayed for any reason, isolate FMC management interfaces from the internet and restrict access to trusted admin IPs only
- Assume any FMC that was internet-accessible between January 26 and March 4 may have been compromised — initiate threat hunting for webshell activity, unexpected root processes, and lateral movement from FMC host IPs
- Check Zscaler and Amazon's published IOC lists for Interlock's specific C2 infrastructure and pivot indicators
- For organizations running Cisco ASA, FTD, or other FMC-managed appliances, audit your rule sets for unauthorized modifications since January 26

### **Langflow CVE-2026-33017 (CVSS 9.3) — RCE in 20 Hours from Advisory to Exploit, No PoC Needed, CISA Now Requires Federal Patch by April 8**

The AI agent framework attack surface struck again on March 17 when Langflow published a detailed security advisory for CVE-2026-33017, a critical missing-authentication combined with code injection vulnerability in its public flow build endpoint. Sysdig's Threat Research Team observed the first exploitation attempts in the wild within 20 hours — and notably, no public proof-of-concept code existed at the time. Attackers reverse-engineered a working exploit directly from the advisory description, scanned the internet for vulnerable instances, and began harvesting API keys and credentials from compromised Langflow deployments. CISA added CVE-2026-33017 to its Known Exploited Vulnerabilities catalog on March 25, requiring federal agencies to remediate by April 8. The technical root cause is identical to CVE-2025-3248 (CVSS 9.8), another critical Langflow RCE from last year — the same `exec()` call without sandboxing appears in a different endpoint: `/api/v1/build_public_tmp/{flow_id}/flow`, which is intentionally unauthenticated to support public flows, making an authentication-only fix structurally impossible without removing the data parameter entirely.

Key findings:

- **CVE-2026-33017 (CVSS 9.3)** — missing authentication + code injection; affects Langflow ≤ 1.8.1; fixed in 1.9.0.dev8
- **20-hour exploit timeline** — no PoC existed; attackers built exploits from the advisory description alone
- **Impact of exploitation**: read environment variables; access/modify files; inject backdoors; obtain a reverse shell; harvest AI provider API keys and cloud credentials stored in the Langflow environment
- **CISA KEV listing** — federal agencies must remediate by April 8, 2026
- **Same root cause as CVE-2025-3248** — Langflow's `exec()` architecture has now yielded two independent critical CVEs; the third may already exist

> **"The collapse from months-long exploitation timelines to same-day weaponization is a structural shift in how vulnerabilities are operationalized. Advisories are now effectively a starting pistol."** — Sysdig Threat Research Team

This is the second Langflow critical RCE in less than a year, following CVE-2025-3248. Langflow is the visual low-code AI agent builder used by organizations to rapidly prototype and deploy AI workflows without deep coding expertise — which means it's most prevalent in environments where security review is lightest. The credential harvesting observed in active exploitation puts every AI provider API key, database credential, and cloud service token accessible from a compromised Langflow instance at risk.

**Immediate actions:**
- Update Langflow to 1.9.0.dev8 or the latest stable release immediately — do not run 1.8.1 or earlier in any internet-accessible configuration
- Rotate all AI provider API keys (OpenAI, Anthropic, Google, Mistral, Cohere) and cloud credentials accessible from any Langflow deployment
- Audit Langflow access logs for POST requests to `/api/v1/build_public_tmp/` from external IPs
- If Langflow cannot be patched immediately, block external access to the `/api/v1/build_public_tmp/` endpoint at the network or WAF layer
- Consider whether Langflow's public flow feature is required for your use case — if not, disable it entirely

### **35 CVEs in One Month Traced to AI-Generated Code — Georgia Tech's Vibe Security Radar Puts Real Numbers on the Vibe Coding Debt Problem**

Georgia Tech's Systems Software & Security Lab (SSLab) published updated data from the Vibe Security Radar project this week that landed like a bucket of cold water on the "AI makes code faster and safer" narrative: at least 35 CVEs disclosed in March 2026 were directly attributable to AI-generated code shipped to production. That's up from six in January and 15 in February — a near-6x acceleration in three months. The project tracks 50 AI coding tools across public vulnerability databases (CVE.org, NVD, GHSA, OSV, RustSec), traces the commit that introduced each bug, and identifies whether an AI tool's signature is present. Of 74 confirmed cases to date, Claude Code appeared most frequently — though researcher Hanqing Zhao noted this is largely because Claude Code "always leaves a signature" in commits, while tools like GitHub Copilot's inline suggestions leave no trace and are structurally harder to attribute. The Register's coverage added the critical caveat: the 74 confirmed cases are the floor, not the ceiling.

Key findings:

- **35 AI-code CVEs in March 2026 alone** — up from 6 (January) and 15 (February); trajectory is exponential
- **74 total confirmed cases** — across 50 AI coding tools tracked (Claude Code, Copilot, Cursor, Devin, Windsurf, Aider, Amazon Q, Google Jules)
- **Attribution bias** — Claude Code appears most frequently because it signs commits; copilot-style inline suggestions are invisible to attribution, likely understating the true count significantly
- **Attack surface**: the same patterns AI tools learn from repositories — including vulnerable patterns — get reused as "approved patterns" even when the original was insecure
- **UK NCSC is watching**: the NCSC Head has publicly urged industry to develop vibe coding safeguards following the Georgia Tech data

> **"Everyone is saying AI code is insecure, but nobody is actually tracking it. We want real numbers. Not benchmarks, not hypotheticals — real vulnerabilities affecting real users."** — Hanqing Zhao, Founder, Vibe Security Radar, Georgia Tech SSLab

The meta-problem is structural: when AI coding agents learn from codebases containing vulnerable patterns and apply those patterns to new implementations, the vulnerability becomes a feature of the tool's output distribution. Code review wasn't designed to catch this class of issue, and the speed of vibe-coded deployments means review is skipped entirely in many cases. NCSC's involvement signals that regulatory pressure on AI coding practices is coming — the only question is timing.

**Immediate actions:**
- Add AI-code vulnerability scanning to your SAST pipeline — tools like Semgrep, Snyk, and CodeQL don't care whether the code was written by a human or an LLM; make them mandatory
- Review any AI-generated code that was pushed to production in Q1 2026 without security review — the March data suggests the volume of AI-introduced vulnerabilities is material
- For teams using Claude Code, Cursor, or Copilot for production code: establish a security review gate before merge that specifically tests for the vulnerability classes most common in AI-generated code (injection flaws, insecure deserialization, path traversal, missing authentication checks)
- Bookmark the Vibe Security Radar (vibe-radar-ten.vercel.app) for your threat intelligence rotation — it's the first real-time tracker for this vulnerability class

## Technical Deep Dives

### **README Injection: AI Coding Agents Exfiltrate Sensitive Files 85% of the Time When Attackers Hide Instructions in Repository Documentation**

Research published this week from a multi-institution team and covered by Help Net Security documents a new indirect prompt injection attack class targeting AI coding agents: malicious instructions embedded in repository README files that cause agents to exfiltrate sensitive local files to attacker-controlled servers during routine project setup. The attack works because AI coding agents — Claude Code, GPT-based agents, Gemini — read and execute README setup instructions as part of their autonomous workflow. Attackers can insert a step that looks like a normal configuration or file sync operation; the agent executes it without checking whether the action exposes sensitive data. The benchmark dataset (ReadSecBench, 500 README files from open-source repositories in Java, Python, C, C++, and JavaScript) showed the attack succeeded in up to 85% of cases across Claude, GPT, and Gemini agents.

Key findings:

- **85% success rate** — across Claude, GPT, and Gemini agents; attack succeeded regardless of repository language or malicious instruction placement within the document
- **No CVE required** — this is not a software vulnerability; it's a design property of how AI agents process natural language instructions with tool access
- **Exfiltrated data in tests**: configuration files, logs, environment variables, SSH keys, and other local sensitive data sent to attacker-controlled servers
- **Attack vector**: any public open-source repository that a developer clones and asks an AI agent to set up is a potential delivery mechanism

This attack is a concrete realization of what the OWASP Agentic AI Top 10 Risk #1 (Agent Goal Hijacking) describes in the abstract. It also represents the flip side of the Anthropic/OpenAI/Google README advisory covered earlier this month: the same attack class works against all three providers' coding agents in production. The fix is not primarily technical — it requires agents to develop skepticism about file transfer and network operations embedded in documentation, which current RLHF training does not reliably produce.

**Immediate actions:**
- When using AI coding agents to set up new repositories, review the README manually before allowing the agent to execute setup steps — specifically look for any file transfer, upload, or sync commands
- Configure your AI coding agent's tool permissions to require explicit confirmation for any outbound network request or file transfer to external endpoints
- For teams managing open-source repositories: audit your README for any instructions that could be mistaken for legitimate setup steps while actually performing data exfiltration
- Treat any repository cloned from an untrusted or unfamiliar source as a potential prompt injection vector — apply the same scrutiny you would to running arbitrary code

### **Meta's Rogue AI Agent Incident: Internal AI Gave Wrong Technical Advice, Employee Followed It, Sensitive Data Exposed for Two Hours**

Meta confirmed a security incident — first reported by The Information and subsequently confirmed to The Guardian — in which an internal AI agent gave incorrect technical advice to an engineer on an internal forum, and the engineer implemented the advice, causing a large amount of sensitive user and company data to be exposed to Meta employees for approximately two hours. Meta's spokesperson characterized the incident as "no user data was mishandled" and noted that a human advisor could have made the same error. But the security framing understates what happened: an AI agent was embedded in an internal engineering workflow with enough authority that a single incorrect response led to a material data exposure, and the engineer executed the advice without independent verification of the security implications. The Guardian's reporting contextualized this as part of a pattern: Amazon also experienced at least two outages related to AI tool deployments, and multiple Amazon employees reported glaring errors, sloppy code, and reduced productivity from the company's AI integration push.

Key findings:

- **Data exposed**: sensitive user and company data, visible to Meta engineers for ~2 hours
- **Root cause**: AI agent gave inaccurate technical advice; human followed it without security validation
- **Pattern of incidents**: this follows Amazon AI-related outages and mirrors the broader agentic AI risk that the OWASP Agentic AI Top 10 formalizes
- **Industry trajectory**: Armis head of threat intelligence Michael Freeman predicted "by mid-2026, at least one major global enterprise will fall to a breach caused or significantly advanced by a fully autonomous agentic AI system" — the Meta incident isn't that prediction fulfilled, but it's the precursor pattern

> **"This breach is one of several recent high-profile incidents caused by the increasing use of AI agents within US tech companies."** — The Guardian, March 20, 2026

The security community's reaction to the Meta incident has been measured skepticism toward the "no user data was mishandled" framing. The incident demonstrates that the blast radius of an AI agent giving confident but incorrect advice is no longer limited to the individual developer — in an integrated engineering workflow, one wrong agentic response can trigger a data exposure affecting an entire organization. The human-in-the-loop assumed to be a safeguard is being systematically optimized away by the same productivity pressure driving AI adoption.

**Immediate actions:**
- Establish a policy that AI agent advice for any action that modifies access controls, data exposure, or security configurations requires independent human verification before execution — the meta lesson from the Meta incident
- For AI agents embedded in internal engineering workflows: implement explicit output tagging that identifies "security-sensitive" actions (anything touching ACLs, data access policies, network exposure) and requires human sign-off before execution
- Audit what AI agents in your organization have authority to advise on without guardrails — define the boundary between "AI can suggest" and "AI can execute without human review"

## Five Things to Take Into the Rest of the Day

1. **The Cisco FMC zero-day is a case study in why "low-severity" revisits are mandatory after a vendor suffers a supply-chain-level compromise.** Interlock had this zero-day for 36 days before Cisco published. The FBI Director's Gmail was already characterized as a "historical" breach. F5 BIG-IP's "DoS-only" reclassification happened after a nation-state spent 12 months inside their source code repository. The pattern is consistent: when a vendor's source code or internal systems are compromised by a sophisticated actor, the initial severity assessment on subsequently disclosed vulnerabilities should be treated as a floor, not a ceiling. Build a protocol for revisiting severity classifications whenever a vendor discloses a contemporaneous supply chain or source code compromise.

2. **The 20-hour exploitation window for Langflow CVE-2026-33017 eliminates "we'll patch in the next sprint" as a viable response to AI framework CVEs.** The development cycle of security programs wasn't designed for same-day weaponization. Traditional vulnerability management assumes weeks between disclosure and active exploitation — enough time for a patch cycle, a risk acceptance decision, a CAB approval. Twenty hours is not a patch cycle. It's barely a standup meeting. Any organization running AI agent infrastructure (Langflow, LangChain, LangGraph, AutoGPT, CrewAI, or comparable frameworks) needs a break-glass procedure specifically for AI framework CVEs that bypasses normal change management timelines — analogous to the emergency patching procedures that exist for hypervisor and network device CVEs.

3. **Georgia Tech's 35 AI-code CVEs in one month is the vibe coding debt arriving as real-world exploitable vulnerabilities.** The argument for AI-assisted coding has always included the claim that AI code is reviewed and corrected by the human in the loop. The Vibe Security Radar data shows what happens when that claim isn't enforced operationally: the same class of vulnerabilities (injection flaws, missing authentication, deserialization) that took the security industry decades to systematically reduce in human-written code is now being regenerated at scale by AI tools that learn from historically vulnerable codebases. The fix isn't to stop using AI coding tools — it's to treat AI-generated code with the same (or higher) mandatory security scrutiny as junior developer output going to production.

4. **The Meta rogue AI agent incident and the README injection research together describe a single failure mode: AI agents acting on natural language instructions without security-aware skepticism about what those instructions are asking them to do.** In the Meta case, the agent gave advice; the human executed it without verifying the security implications. In the README injection case, the agent executed instructions from an external document without verifying whether those instructions were authorized by the user. Both failures have the same structural fix: security-sensitive actions (data exposure, network transmission, access control modification) need an explicit, out-of-band authorization check that cannot be satisfied by the same natural language instruction that triggered the action. This is the agent equivalent of "require MFA for sensitive operations" — and it's not implemented in any production AI coding agent by default.

5. **Sunday emergency patch windows are the new normal for security operations teams in 2026, and the change management frameworks that govern them haven't caught up.** The CISA March 29 deadline for Cisco FMC exists because the threat was already active for 36 days before the advisory. The practitioner communities are documenting a real operational problem: change advisory boards that don't have an expedited approval path for active-exploitation, CISA-directed patching are creating compliance gaps that attackers benefit from. The structural fix requires separating the emergency response protocol for CISA KEV-listed, actively exploited vulnerabilities from the routine patch management cycle — treating them as incident response actions rather than scheduled maintenance.
