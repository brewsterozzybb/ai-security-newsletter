# AI Security Newsletter — March 18, 2026

## Headliners

Today's thread: the **perimeter is dead, and the sandbox was always fiction**. Three converging stories make the point — DNS-based sandbox breakout in Amazon Bedrock proves AI code execution environments aren't as isolated as advertised; invisible Unicode characters are compromising developer supply chains in ways no human reviewer can catch; and Repello AI's data shows MCP tool poisoning succeeds 72.8% of the time against the best models on the market. Add two zero-days in Chrome (CISA-mandated patch deadline March 27), a critical unpatched telnetd RCE, and Apple's first-ever Background Security Improvement patch — and March 18 is a reminder that classic infrastructure vulnerabilities and AI-native attack surfaces are now on the same timeline.

## Breaking News & Phase Shifts

**[Amazon Bedrock AgentCore DNS Sandbox Breakout — BeyondTrust Discloses Data Exfiltration Path](https://thehackernews.com/2026/03/ai-flaws-in-amazon-bedrock-langsmith.html)**

BeyondTrust researchers revealed Monday that Amazon Bedrock AgentCore Code Interpreter's "no network access" sandbox mode permits outbound DNS queries — a gap attackers can weaponize to establish bidirectional C2 channels and exfiltrate data without crossing the TCP/UDP boundary that defenders monitor. The attack chain: connect to an attacker-controlled nameserver, tunnel commands via DNS A record queries, return results via subdomain exfiltration. If the Code Interpreter's IAM role is overprivileged (a common misconfiguration), the blast radius extends to any S3 bucket, database, or AWS resource the role can reach. Separate findings cover LangSmith and SGLang (CVSS 7.5 for the Bedrock flaw; no CVE assigned yet). The core lesson is architectural: sandbox guarantees that block TCP/HTTP but allow DNS are not sandboxes. Amazon has been notified and is addressing the misconfiguration. **Practitioner guidance:** Audit IAM roles assigned to any AI code execution service immediately — overprivileged roles are the multiplier. Block DNS egress at the network perimeter for AI workloads where code execution is involved. Treat "managed isolation" claims from any cloud AI service as hypotheses to be tested, not guarantees.

**[Chrome CVE-2026-3909 & CVE-2026-3910: Two Zero-Days Patched, CISA KEV-Listed with March 27 Deadline](https://thehackernews.com/2026/03/google-fixes-two-chrome-zero-days.html)**

Google patched two high-severity Chrome zero-days under active exploitation — CVE-2026-3909 (CVSS 8.8, out-of-bounds write in Skia graphics library) and CVE-2026-3910 (CVSS 8.8, inappropriate implementation in the V8 JavaScript/WebAssembly engine enabling sandbox RCE via crafted HTML). Both were discovered internally by Google on March 10 and are confirmed in-the-wild. CISA added both to the Known Exploited Vulnerabilities catalog on March 13, requiring Federal Civilian Executive Branch agencies to apply fixes by March 27. This is the third pair of actively weaponized Chrome zero-days since January 2026 — a pace that should prompt enterprises to reconsider manual patching cadences for browser infrastructure. Chromium-based browsers (Edge, Brave, Opera, Vivaldi) are also affected and awaiting vendor patches. **Practitioner guidance:** Update Chrome to 146.0.7680.75/76 (Windows/macOS) or 146.0.7680.75 (Linux) now. Enable auto-update policies for all Chromium-derived browsers across managed fleets. If you run FCEB-adjacent infrastructure, March 27 is your hard deadline — not a suggestion.

**[CVE-2026-32746: Critical Unpatched Telnetd RCE — Unauthenticated Root via Port 23, No Fix Until April 1](https://thehackernews.com/2026/03/critical-telnetd-flaw-cve-2026-32746.html)**

Dream Security's researcher Adiel Sol disclosed a CVSS 9.8 pre-authentication buffer overflow in GNU InetUtils telnetd (all versions through 2.7) affecting the LINEMODE Set Local Characters (SLC) suboption handler. One network connection to port 23 is sufficient — no credentials, no user interaction, no special network position required. Successful exploitation gives the attacker remote root on any system where telnetd runs under root (the default configuration via inetd/xinetd). The flaw was reported to GNU InetUtils on March 11; a patch is expected no earlier than April 1. The relevant question for 2026: who still runs telnetd? The answer is more organizations than should, particularly in OT/ICS environments, embedded Linux appliances, and legacy network infrastructure that also increasingly manages AI inference hardware. **Practitioner guidance:** Immediately disable telnetd if it is not operationally required — it is not required in most environments. For environments where it is needed, block port 23 at the network perimeter and host firewall, run telnetd without root privileges where possible. Shodan your own external attack surface for port 23 exposure today.

**[Apple CVE-2026-20643: First Background Security Improvement Patch Fixes WebKit Same-Origin Bypass](https://thehackernews.com/2026/03/apple-fixes-webkit-vulnerability.html)**

Apple deployed its first-ever Background Security Improvement (BSI) — a new rapid patch delivery mechanism — to fix CVE-2026-20643, a cross-origin issue in WebKit's Navigation API that allows maliciously crafted web content to bypass the same-origin policy on iOS 26.3.1, iPadOS 26.3.1, and macOS 26.3.1/26.3.2. Researcher Thomas Espach discovered the flaw. The BSI mechanism — analogous to Apple's earlier Rapid Security Response system — delivers targeted patches for Safari, WebKit, and system libraries without requiring a full OS update. This is architecturally significant: Apple can now patch WebKit vulnerabilities silently in the background, ahead of the user update cycle. The same-origin policy is a foundational browser security boundary; its bypass enables cross-site data access, credential theft, and session hijacking from maliciously crafted pages. **Practitioner guidance:** Ensure "Automatically Install" Background Security Improvements is enabled in Settings > Privacy and Security on all managed Apple devices. This patch is delivered automatically if the toggle is on — verify fleet compliance, not individual devices. MDM policy should enforce BSI auto-install going forward.

## Technical Deep Dives

**[Invisible Unicode Supply Chain Attack: 150+ GitHub and npm Packages Use Private Use Area Characters to Hide Malware](https://arstechnica.com/security/2026/03/supply-chain-attack-using-invisible-code-hits-github-and-other-repositories/)**

Aikido Security documented an active supply chain campaign using Unicode Private Use Area (PUA) code points — characters invisible to humans and most static analysis tools, but fully executable by JavaScript interpreters — to conceal malicious payloads in over 150 npm packages and GitHub repositories. The technique evolved from a 2024 research finding that AI chatbots could read and follow PUA-encoded prompt injection instructions; attackers adapted it to traditional malware delivery. The decode-and-eval pattern (`eval(Buffer.from(s(backtick-string)).toString('utf-8'))`) looks like an empty string to any code reviewer. In past incidents the decoded payload fetched a second-stage script via Solana as a delivery channel, targeting credentials and environment variables. Similar packages appeared in the VS Code marketplace. The full campaign scope is likely larger — many packages were deleted after upload. **Practitioner guidance:** Add invisible character detection to your supply chain scanning pipeline. Standard SAST and SCA tools do not detect PUA-encoded payloads — you need Unicode normalization checks. Review any recently-added npm or GitHub Actions dependencies against the indicators from Aikido's disclosure. This technique is now documented in the wild; treat any package with unexpected Unicode characters in source files as a potential carrier.

**[MCP Tool Poisoning at 72.8% — Repello AI Research Shows More Capable Models Are More Vulnerable, Not Less](https://repello.ai/blog/mcp-security)**

Repello AI's comprehensive MCP security analysis, drawing on the MCPTox benchmark and real-world deployment data, documents that MCP tool poisoning attacks succeed 72.8% of the time against leading models including o1-mini, DeepSeek-R1, and Claude 3.5 — and that model capability correlates with higher, not lower, susceptibility (more capable models read and follow tool descriptions more faithfully, making them better attack targets). 82% of MCP server implementations contain file system operations vulnerable to path traversal; 53% rely on long-lived static secrets for authentication. The report documents a real-world case: an autonomous AI bot compromised Aqua Security's Trivy repository (32,000 GitHub stars) by exploiting MCP trust assumptions. Pre-deployment audits miss rug pulls, schema mutations, and cross-server hijacking — runtime monitoring is the only defense that scales. **Practitioner guidance:** Stop relying on "vet your servers at install time" as your primary MCP control. Implement runtime monitoring of MCP tool calls, validate tool descriptions haven't changed between sessions, enforce short-lived credentials rather than static API keys, and scope file system access to explicit allowlists. The MCPTox success rate of 72.8% means probabilistic attacks against your production MCP deployment are a near-certainty over time, not a theoretical risk.

**[Pentera 2026 CISO Survey: 67% Lack AI Visibility, 75% Using Legacy Controls to Secure AI Infrastructure](https://thehackernews.com/2026/03/ai-is-everywhere-but-cisos-are-still.html)**

Pentera's AI and Adversarial Testing Benchmark Report 2026 — based on 300 US CISOs — quantifies the security gap that practitioners have been describing qualitatively: 67% of CISOs have limited visibility into AI usage across their organization, none report full visibility, 75% are extending legacy security controls (endpoint, application, cloud, API) to cover AI infrastructure, and only 17% cite budget as the primary constraint. The top barriers are skills shortage (50%), limited visibility (48%), and insufficient AI-specific tooling (36%). The critical implication: security leaders know the problem and have the budget — they lack the expertise and the right instruments. Meanwhile, the attack surface documented throughout this week's newsletters is actively exploited. The capability-control gap isn't closing; it's widening. **Practitioner guidance:** The skills gap is your highest-leverage investment target. AI security upskilling (MITRE ATLAS, OWASP LLM Top 10, practical agentic threat modeling) costs less than the tools you'll need to compensate for operating blind. If 67% of your peer CISOs are flying without AI visibility, that's a benchmark floor, not an acceptable standard. Build your AI asset inventory this quarter.

## Five Things to Take Into the Rest of the Day

1. **The Bedrock DNS finding is the canary for every AI sandbox claim in your stack.** "No network access" is not a guarantee — it's an architecture configuration that needs verification. Every managed AI code execution service your organization uses (Bedrock, LangSmith, Azure AI Studio, Google Vertex AI code execution) should be audited against the same DNS egress question. Block DNS at the network perimeter for AI workloads, audit IAM role scopes for any AI code execution service, and assume that any cloud vendor's "isolation" needs to be independently confirmed. The BeyondTrust research is a repeatable test — run it against your own environment.

2. **Invisible Unicode is now a supply chain attack vector, not just a prompt injection curiosity.** In 2024 it was an academic demonstration that AI could read invisible text. In 2026 it's 150+ npm packages with production backdoors. If your software composition analysis (SCA) tool doesn't check for Unicode PUA characters in source files, it is blind to this entire attack class. Add a Unicode normalization check to your CI/CD pipeline today — it's a one-line grep that could catch what millions of dollars in SCA tooling misses.

3. **MCP tool poisoning at 72.8% means probabilistic success is on the attacker's side.** If you run multiple AI agents connected to MCP servers and those servers process any external input (emails, tickets, web content, documents), you have a near-certainty of a successful tool poisoning event over time. The math: at 72.8% per attempt, after 5 attempts the probability that at least one succeeds is 99.5%. Build your MCP security posture around runtime detection and output validation — not the assumption that tool descriptions are trustworthy.

4. **Mistral Forge changes the enterprise AI security calculus in a way that matters for data governance.** The practical question Forge answers: can an enterprise train and own models on its most sensitive data without routing that data through a US hyperscaler? The answer is now yes, at production scale, with full fine-tuning lifecycle support. For organizations with data sovereignty requirements (GDPR, defense contracts, healthcare), Forge represents a genuine architectural alternative — not just a compliance checkbox. The security team should be in that procurement conversation.

5. **The CISO skills gap is your organization's most honest security KPI right now.** Pentera's finding that 67% of CISOs lack AI visibility, combined with the 75% relying on legacy controls, quantifies the exposure. Legacy controls cannot detect DNS-based AI sandbox breakouts, cannot identify invisible Unicode payloads in npm packages, cannot monitor MCP tool description mutations between sessions. The tools exist; the expertise to deploy and operate them often doesn't. This is a hiring and training problem as much as a technology problem — and it's the gap that every story in today's newsletter exploits.
