### **3. CVE-2026-26030 (CVSS 9.8): Critical RCE in Microsoft Semantic Kernel Python SDK — AI App Supply Chain at Risk**

Microsoft disclosed a **critical remote code execution vulnerability** in the Semantic Kernel Python SDK's `InMemoryVectorStore` filter expression parser. Attackers can inject malicious Python code via crafted filter expressions passed to `similarity_search_with_score` or `similarity_search_with_relevance_scores` methods, triggering arbitrary code execution in the application context. All versions prior to the patched release are affected.

**The supply-chain exposure:** Semantic Kernel is Microsoft's primary AI orchestration framework — the layer enterprises use to build AI applications on top of Azure OpenAI, Claude, and other models. It is the backbone of a significant fraction of enterprise AI deployments in the Microsoft ecosystem. A CVSS 9.8 RCE in a filter expression parser means: any enterprise AI application that handles similarity search and accepts user-influenced filter input is a breach surface until patched. The blast radius is proportional to how many enterprise AI apps are built on Semantic Kernel — which is large.

**Why vector store vulnerabilities are the new SQL injection:** The filter expression attack pattern here is structurally identical to SQL injection in traditional applications — attacker-controlled input parsed and executed in a privileged context. The security community spent 20 years learning to sanitize SQL. We are now in the first wave of learning to sanitize LLM framework filter expressions. Every AI orchestration framework with a query or filter interface should be audited for this class of vulnerability.

**Practitioner guidance:** Patch Semantic Kernel SDK immediately. Audit all enterprise AI applications for user-controlled inputs that flow into `similarity_search_with_score`, `similarity_search_with_relevance_scores`, or any filter expression parser in the SDK. Implement strict input validation for all parameters that flow into vector store queries — treat them as untrusted user input, not trusted API parameters.

### **4. CVE-2026-26118: Azure MCP Server SSRF — Token Theft and Cloud Privilege Escalation**

March Patch Tuesday brought another MCP-specific CVE: **CVE-2026-26118**, a high-severity **Server-Side Request Forgery vulnerability in Azure MCP Server Tools** that allows attackers to steal authentication tokens and escalate privileges within Azure environments.

**Why SSRF in MCP is qualitatively different from SSRF in web apps:** An SSRF in a traditional web application reaches internal network resources. An SSRF in an Azure MCP Server reaches cloud control plane resources — the identity tokens, role assignments, and resource management APIs that control entire cloud environments. This is a lateral movement primitive from the AI orchestration plane directly into the cloud control plane. An attacker who exploits this doesn't just reach an internal service — they potentially reach the keys to the Azure kingdom.

**The MCP infrastructure attack surface geometry:** MCP servers sit at the intersection of AI agents (which have operational permissions) and enterprise infrastructure (which has data and control plane access). Every MCP server is a bridge. An SSRF in that bridge doesn't move laterally within the application — it moves laterally between the AI plane and the infrastructure plane, which is a much more consequential boundary crossing.

**Practitioner guidance:** Verify March Patch Tuesday patching status for Azure MCP Server Tools. Audit network segmentation between MCP server infrastructure and cloud control plane APIs. Implement least-privilege authentication for MCP-to-Azure connections — MCP servers should not have management-plane Azure credentials. Monitor for anomalous token usage patterns originating from MCP server IP ranges.

### **2. Multi-Turn Jailbreaks: 92% Success Rate Across Open-Weight Models — Single-Turn Defenses Are Obsolete**

New research documenting **multi-turn jailbreak attacks** — where adversarial intent is distributed across extended conversations rather than a single prompt — achieved a **92% success rate across eight open-weight models**. A companion study testing 36 LLMs against 144 attack variations found 56% of attacks succeeded across all architectures.

**The architectural implication:** Single-turn content filtering — where each prompt is evaluated in isolation — is insufficient against conversational jailbreaking. A conversation that begins with innocuous prompts and gradually steers toward disallowed content will bypass single-turn guardrails that would catch a direct attack in prompt #1. Most enterprise AI implementations are not designed to maintain adversarial context across conversation turns.

**OWASP Agentic Top 10 connection:** OWASP's newly-published Agentic Top 10 lists goal hijacking and memory poisoning as top risks — both of which are enabled by multi-turn manipulation. The OWASP framework maps directly to the attack pattern these studies document: long-horizon adversarial conversations that look legitimate at each individual step but collectively execute a disallowed objective.

**Practitioner guidance:** Implement conversation-level safety monitoring, not just per-turn filtering. Anomaly detection that tracks semantic drift across a conversation (toward sensitive topics, toward disallowed capability patterns) provides detection coverage that per-turn filtering misses. For high-stakes AI deployments, consider session-level human review triggers when conversation trajectories match multi-turn adversarial patterns.

### **4. GitHub Copilot Passive Prompt Injection → Full Repository Takeover**

Researchers demonstrated that a **malicious GitHub Issue triggers full repository takeover via passive prompt injection in GitHub Copilot** — with activation the moment a developer opens a Codespace. No user interaction with the AI is required. This is zero-touch prompt injection at the CI/CD and source control layer.

**Why this is structurally different from previous prompt injection findings:** Traditional prompt injection required the user to paste malicious content into an AI chat interface. This attack is triggered by the *environment* the AI operates in — the repository, the issue tracker, the ambient context the AI reads as part of its normal workflow. The attacker doesn't need to directly interact with the AI at all. They just need to create a malicious GitHub issue. The AI reads the issue as context. The malicious instruction executes.

**The connection to HackerBot-Claw (March 10):** HackerBot-Claw used 2,000-word "promptware" to compromise developer AI assistants in CI/CD pipelines. This Copilot finding is the same attack class — ambient environment as attack vector — but in a different AI integration. The pattern is generalizing: any AI that reads its environment as context (Copilot reading repos and issues, Claude reading calendar invites via DXT, Gemini reading emails in Workspace) can have its behavior controlled by adversaries who write to that environment.

**Practitioner guidance:** Treat all inputs to AI-integrated developer tooling as potentially adversarial — including issue tracker content, PR descriptions, code comments, and external documentation fetched during AI assistance. Implement output monitoring for Copilot actions (especially credential access, network calls, and file system writes) that are inconsistent with the ostensible task context. Restrict Copilot's Codespace permissions to the minimum required for the specific use case.
