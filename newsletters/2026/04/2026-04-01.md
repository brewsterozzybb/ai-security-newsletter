## Breaking News

### **Claude Authored a Complete FreeBSD Kernel RCE Exploit — Stack Overflow to Root Shell in 8 Hours, No Human Wrote a Line of Exploit Code**

Security researchers at Calif.io published today the most significant AI-assisted exploit development demonstration yet documented: Claude — given only a FreeBSD security advisory and access to a VM — autonomously developed a fully functional remote kernel code execution exploit for CVE-2026-4747, a stack buffer overflow in FreeBSD's `kgssapi.ko` RPCSEC_GSS module. The vulnerability itself was credited to "Nicholas Carlini using Claude, Anthropic" in FreeBSD's original March 26 advisory. The Calif.io team then took that published advisory on March 29 and asked Claude to write an exploit. By 5:00 PM PDT the same day, Claude had delivered two independent, working exploits — both achieving a remote root shell on a fresh FreeBSD 14.4 VM — using different exploitation strategies. Total wall clock time: approximately eight hours, with Claude's active working time around four hours.

Key findings:

- **CVE**: CVE-2026-4747 — FreeBSD `kgssapi.ko` RPCSEC_GSS `svc_rpc_gss_validate()` stack buffer overflow; no KASLR, no integer-array stack canaries on FreeBSD 14.x
- **Attack surface**: NFS server with `kgssapi.ko` loaded (port 2049/TCP); requires valid Kerberos ticket (any unprivileged user with AD/FreeIPA access qualifies)
- **Affected versions**: FreeBSD 13.5 (<p11), 14.3 (<p10), 14.4 (<p1), 15.0 (<p5)
- **Exploit mechanics**: 15-round multi-packet delivery (shellcode doesn't fit in one packet); Claude independently devised De Bruijn pattern analysis for offset debugging, `kthread_exit()` for clean thread hijacking, `kproc_create()` + `kern_execve()` for kernel-to-userland transition, and DR7 register clearing to fix a hardware breakpoint bug in child processes
- **Timeline**: Advisory published March 26 → Exploit request March 29 9:45AM PDT → Working root shell 5:00PM PDT same day
- **HN signal**: 80 points, 28 comments — community consensus is that exploit *development* (not just bug finding) crossing the AI-capability threshold is the significant event

> **"Finding a bug and exploiting it are very different things. Exploit development requires understanding OS internals, crafting ROP chains, managing memory layouts, debugging crashes, and adapting when things go wrong. This has long been considered the frontier that only humans can cross. Well, for X = exploit development, that line just moved."** — Calif.io, MAD Bugs writeup, April 1, 2026

The nuance that HN commenters flagged: Claude did not independently discover CVE-2026-4747 — the vulnerability was found first (with Claude's assistance) by Nicholas Carlini. What Calif.io demonstrated is the *exploitation* half of the pipeline. The practical threat model shift: any attacker who can point Claude at a published CVE advisory for a system lacking modern mitigations (KASLR, stack canaries) can now generate functional exploitation code in hours, not weeks. The barrier to weaponizing disclosed kernel vulnerabilities has materially dropped.

**Immediate actions:**
- Patch FreeBSD immediately: 13.5-p11, 14.3-p10, 14.4-p1, and 15.0-p5 address CVE-2026-4747; unpatched NFS servers with `kgssapi.ko` loaded are now trivially exploitable
- If you cannot patch immediately, disable NFS Kerberos authentication (`kgssapi.ko`) until patched — the vulnerable code path requires RPCSEC_GSS authentication flavor
- Update your threat model for AI-accelerated exploitation: time-to-weaponization for CVEs affecting systems without modern mitigations is now measured in hours, not weeks — your patch window has shrunk
- Review enterprise NFS exposure: any NFS server with Kerberos auth reachable by non-admin AD/FreeIPA users is in scope for this CVE's exploitation profile

### **Oasis Security Chains Three Claude.ai Vulnerabilities Into Silent Data Exfiltration — No Integrations Required, Google Ads as Delivery Vehicle**

Oasis Security's research team disclosed today what they're calling "Claudy Day": a three-vulnerability chain in the Claude.ai web platform that — when combined — allows an attacker to silently exfiltrate a target's conversation history without requiring any tool integrations, MCP servers, or browser extensions. The chain begins with invisible prompt injection via Claude.ai's pre-filled URL parameter (`claude.ai/new?q=...`), which allows arbitrary HTML tags to be embedded in a prompt that are invisible in the text box but fully processed by Claude when the user hits Enter. The second vulnerability is a data exfiltration path through Anthropic's Files API: from within the code execution sandbox, Claude can upload files to an attacker-controlled Anthropic account — enabling silent extraction of conversation history to a persistent external location. The third is an open redirect on `claude.com` that allowed the attacker-crafted injection URL to be served behind a trusted `claude.com` hostname — enabling Google Ads targeting with a google-validated, claude.com-branded URL that redirects to the malicious prompt. Anthropic has fixed the prompt injection vulnerability; the remaining issues are being addressed.

Key findings:

| Vulnerability | Mechanism | Status |
|---|---|---|
| Invisible prompt injection | HTML tags in `claude.ai/new?q=` parameter — invisible in UI, processed by Claude | **Fixed** |
| Files API exfiltration path | Sandbox allows `api.anthropic.com` connections — conversation history uploaded to attacker's account | Being addressed |
| `claude.com` open redirect | `claude.com/redirect/<target>` redirects without validation — enables google-ads delivery | Being addressed |

- **Attack delivery**: Google Ads targeting (location, industry, demographics, Customer Match for specific email addresses) — precision strikes against known targets via trusted-looking `claude.com` URLs
- **Data at risk in a default session**: conversation history, memory, any business strategy/financial/health/personal information discussed with Claude
- **With MCP/integrations enabled**: blast radius expands to all connected files, APIs, and services — agent can be silently redirected to act on those with full tool access
- **No auth, no extensions**: the attack chain requires only that the victim click a link and press Enter on the pre-filled chat
- **Prior Oasis pattern**: this is their second AI agent disclosure in recent months, following an earlier OpenClaw vulnerability — consistent pattern of chaining agentic capabilities into full attack pipelines

> **"No integrations, no tools, no MCP servers required. The attack works against a default, out-of-the-box claude.ai session."** — Oasis Security, Claudy Day disclosure

The structural lesson: Claude.ai's architecture trusted pre-filled URL prompts to be inert text, and trusted the Files API as a sandboxed outbound path that couldn't reach attacker-controlled infrastructure. Neither assumption held. For enterprise Claude.ai deployments: every integration you add expands the blast radius of a successful prompt injection — the baseline case (no integrations) was already enough for full conversation exfiltration. Organizations deploying Claude with MCP servers, tool access, or enterprise integrations should treat this as a concrete illustration of what a successful prompt injection at the base layer can unlock at the integration layer.

**Immediate actions:**
- Audit your organization's Claude.ai usage: identify users with Claude integrations (MCP servers, Google Drive, GitHub connections) enabled — their blast radius in a successful prompt injection is significantly larger than a default session
- Establish an AI assistant inventory: know which agents are in use, what data they can access, and what tools they can call — this is the prerequisite for meaningful prompt injection risk management
- Educate users that pre-filled prompts, shared Claude links, and clicked URLs opening Claude chat are all potential injection delivery vectors — the attack surface is not just what you type
- Monitor for anomalous Anthropic API calls from your corporate accounts — specifically Files API uploads from users who are not developers or engineers

## Technical Deep Dives

### **CVE-2026-33017: Langflow's AI Pipeline Builder Had an Unauthenticated RCE — Exploited in 20 Hours, Now on CISA KEV**

**CVE-2026-33017** | CVSS 9.3 | Langflow ≤1.8.1 | **Patch: upgrade to 1.9.0**

Langflow — the open-source, low-code visual platform for building AI pipelines with drag-and-drop LLM, vector database, and API integrations — shipped a critical unauthenticated remote code execution vulnerability that CISA added to its Known Exploited Vulnerabilities catalog this week with a patch deadline of April 8. The flaw lives in the `POST /api/v1/build_public_tmp/{flow_id}/flow` endpoint: the endpoint is designed to allow building *public* flows without authentication, but when the optional `data` parameter is supplied, attacker-controlled flow logic replaces the stored flow — and that logic is passed directly to Python's `exec()` with zero sandboxing. Sysdig documented active exploitation beginning within 20 hours of the original disclosure, making this the fastest-weaponized AI-specific CVE yet recorded.

Key findings:

- **Attack prerequisites**: any Langflow instance with at least one public flow (common for demos, chatbots, shared workflows); flow UUID discoverable via shared URLs; no authentication required
- **When `AUTO_LOGIN=true` (the default)**: attacker can create their own public flow in 3 HTTP requests — making this a truly zero-prerequisite unauthenticated RCE
- **Exploitation path**: `GET /api/v1/auto_login` → obtain superuser token → `POST /api/v1/flows/` → create public flow → `POST /build_public_tmp/{flow_id}/flow` with malicious `data` → arbitrary Python execution
- **Exploitation speed**: active in-the-wild attacks observed within 20 hours of disclosure — the fastest weaponization timeline for any AI platform CVE on record
- **Impact**: arbitrary code execution in the context of the Langflow process — full access to any secrets, API keys, and connected data sources the instance can reach
- **CISA KEV deadline**: April 8, 2026

**Immediate actions:**
- Upgrade to Langflow 1.9.0 immediately — this is the only fix; no workaround addresses the root issue
- If upgrade is not immediately possible: disable public flows (`AUTO_LOGIN=false` reduces the zero-prerequisite attack path; network-level blocking of the `build_public_tmp` endpoint reduces exposure)
- Rotate any API keys, database credentials, and LLM provider keys (OpenAI, Anthropic) accessible to your Langflow instance — treat existing deployments as potentially compromised if they were reachable during the disclosure window
- Audit Shodan/Censys for your organization's publicly exposed Langflow instances — the attack requires only network access

### **CVE-2026-22730: SQL Injection in Spring AI's MariaDB Vector Store Lets Attackers Poison RAG Pipelines**

**CVE-2026-22730** | Spring AI MariaDB vector store | Affected: Spring AI with MariaDB vector store integration

A SQL injection vulnerability discovered in Spring AI's MariaDB vector store integration allows attackers with the ability to supply metadata filter values to manipulate database queries — enabling both data exfiltration from the vector store and, in write-capable configurations, injection of poisoned embeddings into the RAG knowledge base. Spring AI's vector store integrations accept metadata filters as part of similarity search queries; the MariaDB implementation fails to properly parameterize these inputs, allowing classic SQL injection through the filter parameter. The security impact is particularly significant in RAG (Retrieval-Augmented Generation) contexts: an attacker who can inject malicious embeddings into the vector store can influence what context the LLM receives for any subsequent query — a vector database poisoning attack that corrupts the AI's knowledge base at the retrieval layer.

Key findings:

- **Vulnerability class**: SQL injection via unsanitized metadata filter parameters in `MariaDbVectorStore.similaritySearch()`
- **Attack surface**: any Spring AI application exposing search or query endpoints that accept user-controlled metadata filter values
- **Impact dimension 1**: data exfiltration — attacker can dump vector store contents including stored embeddings and associated metadata
- **Impact dimension 2**: RAG poisoning — write-capable configurations allow insertion of attacker-controlled embeddings that manipulate LLM responses for downstream queries
- **Why RAG poisoning matters**: unlike prompt injection (which affects one session), vector store poisoning persists — every user querying the RAG system receives responses influenced by the injected content until the store is cleaned

**Immediate actions:**
- Update Spring AI to the latest patched release — check the Spring AI Security Advisories for the specific version addressing CVE-2026-22730
- Audit all Spring AI MariaDB vector store deployments for unexpected content — run a query for recently inserted embeddings to detect potential poisoning
- Implement input validation on any metadata filter parameters exposed to user input in your Spring AI applications
- Review which RAG applications in your environment use Spring AI with MariaDB — any that accept user-controlled filter parameters are in scope

## Five Things to Take Into the Rest of the Day

1. **AI has crossed into exploit development — your patch windows are now measured in hours, not weeks.** The CVE-2026-4747 demonstration wasn't Claude finding a bug; it was Claude doing the hard part — kernel internals, ROP chains, debugging crashes across eight hours of autonomous iteration — that used to require a human expert. The implication for defenders: on systems without modern mitigations (KASLR, stack canaries, CFI), disclosed CVE advisories are now exploitation-ready inputs for any attacker with Claude access. If a vulnerability is public and your system lacks modern mitigations, assume weaponization is already in progress.

2. **Claude.ai's "Claudy Day" is a template, not an isolated incident.** The three-vulnerability chain Oasis Security disclosed — invisible HTML in a URL parameter, Files API as an exfiltration channel, open redirect as a delivery wrapper — is structurally repeatable across every AI assistant that accepts pre-filled prompts or clicks-to-open-chat. The particular exploit was fixed; the *class* of vulnerability persists everywhere AI assistants accept external input and have access to tools that can make outbound connections. Audit your AI assistant deployments for this pattern: what can the agent *do* if its prompt is hijacked, and what can it *exfiltrate* without triggering any alert?

3. **Langflow's 20-hour exploitation window is the new benchmark for AI-platform CVE response.** The time between disclosure and active exploitation for CVE-2026-33017 — 20 hours — is faster than almost any security team's patch deployment cycle. Langflow is not an outlier; it's a preview. AI development platforms (Langflow, Dify, Flowise, and equivalents) are being deployed at startup speed with production data and API key access, and they're being targeted at the same speed attackers moved on Log4Shell. If you have AI pipeline tooling in your environment, treat it with the same urgency as production web servers — not as development tooling.

4. **The 1-bit LLM (PrismML Bonsai) is a security event, not just an efficiency milestone.** A commercially viable reasoning model in 1.15GB that runs at 132 tokens/second on an M4 Pro is not just a performance story — it's the architecture that enables fully local, network-invisible agentic systems. An agent running on a developer's laptop with no network telemetry, no API-layer logging, and no enterprise visibility is an agent your SOC cannot monitor. The security controls you're building for cloud-connected AI agents will not transfer to locally-running models. Start thinking about endpoint telemetry for local model execution now, before Bonsai-class models are in every developer's IDE.

5. **OpenAI at $852B is a governance problem the security community needs to take seriously.** The framing in HN comments — "too big to fail" — is the right frame. At 900M weekly active users and $122B in backing from Amazon, Nvidia, SoftBank, and Microsoft, OpenAI is operating infrastructure that, if disrupted, would have immediate cascading effects on thousands of enterprise workflows. That's a critical infrastructure profile. The same week OpenAI closes this round, Claude.ai disclosed a full-chain exfiltration attack and Langflow (built on OpenAI APIs) shipped a critical RCE into the KEV catalog. Scale creates both systemic risk and systemic accountability pressure. If you're building or deploying OpenAI-dependent workflows, your business continuity plan should include the scenario where OpenAI's infrastructure or API is disrupted — voluntarily or otherwise.
