## 1. Headliners

### The First Documented LLM-Agent Intrusion in the Wild: Sysdig Captures Autonomous Post-Exploitation

On May 30, **[Sysdig](https://www.sysdig.com/blog/ai-agent-at-the-wheel-how-an-attacker-used-llms-to-move-from-a-cve-to-an-internal-database-in-4-pivots)** published the most consequential incident report of the month — a documented intrusion, captured on May 10, 2026, in which an unknown attacker deployed a large language model agent that autonomously drove the entire post-exploitation chain. No human typed a single command after the initial foothold.

**The Attack Chain:**

The breach began with **CVE-2026-39987**, a critical pre-authentication remote code execution vulnerability in **[Marimo](https://github.com/marimo-team/marimo)**, an open-source Python notebook widely used by AI researchers and data scientists. The flaw required no exploit kit: a single WebSocket request to an exposed endpoint produced a fully interactive shell. From there, an LLM agent took over.

The agent's trajectory, reconstructed from Sysdig's forensic analysis:

1. **Credential Harvesting** — The agent extracted two cloud credentials from environment files on the compromised host.
2. **Fanned-Out Egress** — It replayed those credentials through a distributed pool of Cloudflare Workers edge nodes — 12 API calls across 11 distinct IP addresses in 22 seconds — effectively rendering per-source-IP detection useless.
3. **Secrets Manager Extraction** — It retrieved an SSH private key from AWS Secrets Manager.
4. **Lateral Movement** — It launched eight parallel SSH sessions against a downstream bastion server.
5. **Data Exfiltration** — It dumped the full schema and contents of an internal PostgreSQL database in under two minutes.

The entire chain: a little over one hour. One agent. Zero human intervention after the initial breach.

**The Forensic Fingerprints of Machine Operations:**

Sysdig identified four indicators that an LLM agent — not a human — drove the operation:

- **Schema improvisation**: The agent dumped a six-table database whose schema it had never seen, composing `pg_dump` commands on the fly without any pre-staged knowledge.
- **Planning comment leakage**: A Chinese-language planning comment — "看还能做什么" ("see what else we can do") — appeared in the live command stream during a credential search, consistent with LLM chain-of-thought artifacts rather than human chatter.
- **Machine-native command formatting**: Every command was designed for machine consumption: `---` delimiters separating operations, bounded output captures, `less` disabled, and `stderr` discarded to minimize noise.
- **Self-feeding value handoffs**: The agent ran `ls ~/.ssh/id_ed25519*` to confirm a key file existed, then immediately ran `cat ~/.ssh/id_ed25519` to extract its contents — a pattern of tool output feeding the next action.

As Sysdig's threat research team summarized: "A scripted operator builds a per-target playbook and reuses it. An agent operator carries general priors about a class of applications and composes the chain live to best fit its target. The bar becomes inference budget, not playbook authorship."

**Why It Changes Everything:**

This is the first publicly documented case of an LLM agent operating autonomously in a real intrusion — not as a co-pilot, not as a chatbot generating phishing lures, but as the autonomous operator of a complete attack chain. The "attacker no longer needs to see your environment to operate inside it."

For defensive teams, the implications are structural: detection rules written for human behavior patterns (command timings, typing cadence, reconnaissance patterns) will miss machine-driven intrusions entirely. The adaptiveness of agent-driven post-exploitation — where the agent reads the environment, decides what to try next, and keeps going — invalidates the scripted-playbook detection model that most security operations centers still rely on.

The incident also establishes a new forensic category: **LLM artifacts in command streams** (planning comments, delimiter patterns, stderr discard behavior) that defenders can hunt for. But as Sysdig notes, these artifacts are model-specific and will evolve as attacker tradecraft improves.

### Project Glasswing One-Month Results: 10,000+ Vulnerabilities and the New Bottleneck Is Remediation

**[Anthropic](https://www.anthropic.com/glasswing)** published the first quantified results from Project Glasswing's first month of operation, and the numbers reset the industry's understanding of what AI-powered vulnerability discovery means in practice.

**The Numbers:**

| Metric | Value |
|---|---|
| Glasswing partner findings | 10,000+ high-/critical-severity vulns |
| Cloudflare findings | 2,000 bugs (400 high/critical) |
| Open-source projects scanned | 1,000+ |
| Estimated open-source high/critical vulns | 6,202 |
| Total open-source findings (all severities) | 23,019 |
| Average patch time per critical bug | ~2 weeks |

The model has already found vulnerabilities "in every major operating system and web browser." The partners — including Amazon, Apple, Google, Microsoft, JPMorgan Chase, Nvidia, Cisco, Broadcom, and CrowdStrike — collectively identified more than 10,000 serious flaws in their own first-party software after just one month of Mythos Preview access.

**The Remediation Gap:**

The headline number that matters most is the average patch time: approximately **two weeks per high- or critical-severity bug**. At the current discovery rate, Mythos will identify roughly 3,900 critical open-source vulnerabilities per year — on top of whatever partners find internally. The discovery engine is now running faster than the remediation pipeline.

Anthropic confirmed that some maintainers have asked the company to slow down reporting because they lack the engineering capacity to design patches as fast as Mythos files reports. The company has reported 530 high- or critical-severity flaws so far and expects to communicate another 827. Many of these have survived years or decades of human code review.

**A Proactive Defense Success Story:**

The Glasswing results included an operational success that the security community should study carefully: one partner bank used Mythos to detect and block a fraudulent $1.5 million wire transfer mid-execution. That's not vulnerability discovery — it's AI-powered fraud detection running at machine speed inside an existing workflow, and it worked.

**Why It Matters:**

The Glasswing numbers confirm what security practitioners have been warning about since Mythos was first disclosed: AI capability has crossed a threshold where the bottleneck is no longer discovery but remediation. Organizations that build their security strategy around the assumption that their vulnerabilities will remain undiscovered for years need to revise that assumption. The window between disclosure and exploitation is collapsing toward zero. And if AI can find bugs faster than humans can fix them, then the defense strategy must shift toward architectural resilience — because patch velocity alone cannot keep up.

## 2. Breaking News

### FBI Warns of "Kali365": AI-Powered Phishing-as-a-Service That Bypasses MFA

The **[FBI](https://www.ic3.gov/PSA/2026/PSA260521)** issued a public service announcement warning about **Kali365**, a phishing-as-a-service (PhaaS) platform that targets Microsoft 365 accounts by abusing **OAuth device code authentication** — a legitimate Microsoft protocol designed for input-constrained devices like smart TVs and conference room systems.

**How It Works:**

Kali365 exploits the OAuth 2.0 Device Authorization Grant flow. Rather than stealing passwords or intercepting MFA codes directly, the platform:

1. **Generates** a device code via Microsoft's legitimate OAuth flow.
2. **Tricks** the target into entering that code at `microsoft.com/devicelogin` through phishing emails and social engineering.
3. **Captures** the resulting OAuth access and refresh tokens after the victim completes MFA on the legitimate login page.
4. **Grants** the attacker persistent access to the victim's Microsoft 365 account — email, Teams, SharePoint, Salesforce, and all SSO-connected apps — without ever solving an MFA challenge.

The platform includes **AI-generated phishing lures**, automated campaign templates, real-time victim-tracking dashboards, and an adversary-in-the-middle (AitM) mode called "Cookie Link" that proxies victims through attacker-controlled infrastructure to capture authenticated browser sessions and session cookies.

**Operational Scale:**

First observed in April 2026, Kali365 is distributed via Telegram and operates with a business structure: platform admins manage product development, resellers promote the service, and affiliates execute phishing campaigns. **[Arctic Wolf](https://arcticwolf.com/resources/blog/token-bingo-dont-let-your-code-be-the-winner/)** documented widespread campaigns targeting organizations globally, with attackers creating malicious inbox rules to hide their activity and registering new devices in compromised Microsoft environments.

Pricing starts at approximately $250/month — accessible enough for low-skill attackers to deploy enterprise-grade phishing infrastructure.

**Mitigation:**

The FBI recommends organizations:
- Restrict or block OAuth device code authentication flows via Conditional Access policies
- Audit existing device code usage in their environments
- Block authentication transfer policies that allow sessions to move between devices
- Treat unsolicited device code prompts as suspicious — do not enter codes you did not request

**Why It Matters:**

Kali365 represents the commoditization of AI-powered MFA bypass. The platform combines three accelerating trends — device code flow abuse, AI-generated phishing content, and PhaaS business models — into a single subscription service. For enterprise defenders, this means that MFA alone is no longer a sufficient authentication control. Conditional Access policies, token-lifetime restrictions, and user education about device code phishing are now baseline requirements.

## 3. Technical Deep Dives

### Microsoft Open-Sources Agent Framework and Governance Toolkit — Governance Built In, Not Bolted On

Microsoft made two significant open-source releases this week that directly address the security architecture problems highlighted by the Starlette BadHost, SymJack, and TrustFall disclosures: the **[Microsoft Agent Framework (MAF)](https://github.com/microsoft/agent-framework)** and the **[Agent Governance Toolkit](https://github.com/microsoft/agent-governance-toolkit)** .

**Microsoft Agent Framework (MAF):**

MAF is an open, multi-language framework (Python and .NET) for building and deploying production-grade AI agents and multi-agent workflows. On its own, it's a capable entry into a crowded field — OpenAI Agents SDK, Anthropic's MCP ecosystem, LangGraph, and many others. What distinguishes MAF is its sibling project.

**Agent Governance Toolkit:**

This is the more interesting release from a security perspective. The toolkit covers:

- **Policy enforcement** — Define and enforce what agents can and cannot do, with granular controls that extend beyond simple allow/deny lists.
- **Zero-trust identity** — Agents authenticate as distinct principals with bounded identities, not as the user who initiated them.
- **Execution sandboxing** — Agent code runs in constrained environments with filesystem, network, and capability isolation.
- **Reliability engineering** — Observability hooks, retry policies, and failure modes that prevent cascading agent failures.
- **OWASP Agentic Top 10 coverage** — Explicitly addresses the OWASP Top 10 for AI agent systems, including injection, insecure output handling, and excessive agency.

**Why It Matters:**

The Governance Toolkit's architecture — treating agent security as a cross-cutting concern with policy, identity, and sandboxing — is the correct approach for production agent deployments. Most current agent frameworks treat security as an afterthought: the tool permission model is appended, the secrets management is delegated to the developer, and the sandboxing is optional.

Microsoft's entry into this space with a governance-first approach is significant not because Microsoft will dominate agent frameworks (it may or may not), but because it validates that **governance is now a first-class design requirement, not a deployment-time afterthought**. For teams evaluating agent frameworks, the presence or absence of a governance layer should be a primary selection criterion.

### Okta's Answer to Rogue AI Agents: An Identity Layer, Not Another Perimeter

As organizations struggle to answer the question "What AI agents are running in my environment, and what can they access?", **[Okta](https://www.okta.com/newsroom/articles/ai-agents-at-work-2026-agentic-enterprise-security/)** published its approach this week, covered in detail by **[The Register](https://www.theregister.com/ai-ml/2026/05/29/okta-writes-its-own-license-to-kill-rogue-ai-agents/)** .

**The Approach:**

Rather than attempting to rewire every application to accommodate agent access — an approach that practically scales to zero in enterprises with thousands of applications — Okta places an **authorization layer around the agents themselves**. The system:

- **Discovers agents** operating inside the organization across multiple platforms and systems.
- **Maintains a directory of agents** — who they are, what identity they operate under, what permissions they hold.
- **Enforces policy** for what systems each agent may reach, with granular access controls.

As Okta's McKinnon explained to The Register: "We tell you who your agents are. There's a directory of agents."

**Why It Matters:**

The identity-centric approach to agent security is architecturally sound for the same reason identity-centric security won over perimeter-centric security in the cloud era: agents are ephemeral, distributed, and operate across trust boundaries. You cannot firewall them. You cannot network-segment them. You can, however, authenticate and authorize them.

For CISOs currently fielding questions like "Should we let our Claude Code agent access the production database? And how would we even control that if we wanted to?", Okta's model provides a concrete architectural reference: agents get identities, identities get policies, policies get enforced at an authorization layer that sits between the agent and every resource it touches.

The broader point — and one that security teams should internalize — is that **agent security is identity security**. The tooling is early, but the architectural pattern is clear.

### Hacker News: OpenRouter Raises $113M Series B — AI Routing Infrastructure Validated

**[OpenRouter](https://openrouter.ai/announcements/series-b)** raised a $113M Series B, announced May 30, landing at 431 points and 211 comments on Hacker News. The company operates as a routing layer for AI model inference — directing API calls to the most appropriate model based on cost, latency, and capability requirements.

For security teams, OpenRouter's growth matters because **model routing is an emerging attack surface**. If an application routes inference requests through an intermediary that selects which model to call, the routing layer itself becomes a trust boundary — one that must validate model responses, enforce data residency, and resist prompt injection that could influence routing decisions. The Series B validates that inference infrastructure is a core (and rapidly consolidating) market, which in turn means the security of that infrastructure will become a procurement requirement.

## 6. Five Things to Take Into the Rest of the Day

1. **The era of AI-on-AI intrusion is here — rewrite your detection rules.** Sysdig's documentation of the first LLM-agent-driven post-exploitation chain is not a hypothetical. Detection rules based on human behavioral patterns — command timing, reconnaissance cadence, typing inter-arrival times — will miss machine-driven intrusions entirely. Evaluate whether your SOC's detection logic can identify agent-native operations (machine-formatted commands, stderr suppression, tool-output self-feeding patterns).

2. **MFA is no longer sufficient against OAuth device code abuse.** Kali365's device code phishing bypasses MFA entirely by capturing tokens after the victim has authenticated. Organizations should immediately audit OAuth device code flow usage, restrict it via Conditional Access policies, and train users to treat unsolicited device code prompts as suspicious. This is not a theoretical concern — it is actively exploited in the wild.

3. **Your vulnerability management velocity is now the binding constraint.** The Mythos Glasswing results demonstrate that AI-powered vulnerability discovery can outpace human remediation capacity. If your organization's average patch cycle for critical vulnerabilities exceeds two weeks, you are already operating at a deficit. Invest in automated patch deployment, vulnerability triage automation, and architectural defenses (network segmentation, least privilege) that buy time for manual remediation.

4. **Agent governance is not optional — it is the security control that enables safe deployment.** Both Microsoft's Agent Governance Toolkit and Okta's agent directory approach converge on the same architectural principle: agents need distinct identities, bounded permissions, and auditable execution. If your organization is deploying AI agents without these controls, you are running production services without identity management. Start with an agent inventory — you cannot govern what you cannot name.

5. **Defenders need to add "LLM artifact hunting" to their forensic toolkit.** The Sysdig incident established a new forensic category: artifacts of LLM agency in command streams. Planning comments in Chinese (or any language the training data overrepresents), `---` command delimiters, aggressive stderr suppression, and tool-output self-feeding all signal machine-driven operations. Train your threat hunting team to recognize these patterns before they become obfuscated by more sophisticated adversaries.
