## 1. Headliners

### PraisonAI CVE-2026-44338: AI Agentic Framework Auth Bypass Exploited in Under Four Hours

On May 11, 2026, at 13:56 UTC, GitHub published advisory GHSA-6rmh-7xcm-cpxj for PraisonAI — an open-source multi-agent orchestration framework with approximately 7,100 GitHub stars. At 17:40 UTC the same day, Sysdig's threat research team observed the first targeted probe against the vulnerable endpoint. Three hours and forty-four minutes.

**The vulnerability (CVE-2026-44338, CVSS 7.3)** is not subtle. The legacy Flask-based API server shipped in PraisonAI's codebase hardcodes two lines that should never reach production:

```python
AUTH_ENABLED = False
AUTH_TOKEN = None
```

This means that any caller who can reach the server over the network can, without credentials:
- Enumerate the operator's configured agent workflows via `GET /agents`
- Trigger the full configured `agents.yaml` workflow via `POST /chat`
- Exhaust the operator's LLM API quota at will
- Receive the output of `PraisonAI.run()` — which may include sensitive data processed by the agents

The blast radius is entirely dependent on what the operator's agents have been configured to do. An agent with read access to internal databases, file systems, or API credentials is fully exploitable by an unauthenticated network caller. PraisonAI's own advisory acknowledges: "the authentication bypass is unconditional in the shipped legacy server."

The flaw affects all versions from 2.5.6 through 4.6.33. It was patched in version 4.6.34, released by security researcher Shmulik Cohen after responsible disclosure.

**Sysdig's documentation of the exploitation timeline is the most significant part of this story.** The scanner that targeted PraisonAI identified itself as `CVE-Detector/1.0`, originated from IP `146.190.133[.]49`, and ran two passes: the first at generic disclosure paths, the second specifically targeting the known vulnerable endpoints. This was not opportunistic — it was automated, targeted, and operating on a sub-four-hour clock from advisory to scan.

Sysdig has now documented this pattern across multiple AI and developer tooling CVEs in rapid succession:

| CVE | Tool | Time to First Exploitation |
|-----|------|---------------------------|
| CVE-2026-44338 | PraisonAI | 3h 44m |
| CVE-2026-33017 | Langflow | ~20 hours |
| CVE-2026-33626 | LMDeploy | ~12 hours |
| Marimo RCE | Marimo | ~10 hours |

The pattern is consistent: agentic AI framework CVEs are being scanned and exploited within hours of public disclosure. Sysdig attributes this to AI-assisted exploit generation — their Zero Day Clock analysis suggests attackers are now using LLMs to reverse-engineer patches, identify the underlying vulnerability, and generate functional exploit code within minutes of a patch release.

**What operators of AI frameworks and agentic tools need to do:**
1. **Never expose PraisonAI's legacy API server to the internet.** Update to 4.6.34 immediately.
2. **Treat agentic framework CVEs like web application CVEs** — the disclosure-to-exploitation window is now measured in hours, not days.
3. **Run CVE monitoring on AI framework dependencies** with the same urgency as OS and network stack patching.
4. **Assume that any public agentic endpoint without authentication is already being probed** if it has been running for more than a business day after a CVE disclosure.

### Microsoft MDASH: An AI Finds 16 Windows Vulnerabilities Before Attackers Do

This week Microsoft publicly unveiled MDASH — Multi-Model Agentic Scanning Harness — a production-grade AI system that finds, validates, and proves exploitable vulnerabilities in codebases like Windows. It already worked: 16 of the vulnerabilities patched in this month's Patch Tuesday were found by MDASH before any attacker reported them.

**MDASH's architecture** is a structured pipeline of more than 100 specialized AI agents operating in an ensemble of frontier and distilled models:

1. **Threat modeling phase:** Ingests the codebase, builds an attack surface model, identifies candidate code paths
2. **Auditor agents:** Specialized per vulnerability class (memory corruption, auth bypass, use-after-free, etc.), trained on past CVEs and their patches — flagging potential issues in candidate paths
3. **Debater agents:** A second model layer that attempts to refute each auditor finding
4. **Grouping and deduplication:** Semantically equivalent findings are collapsed
5. **Proving phase:** A separate SOTA model proves that flagged vulnerabilities are exploitable

The philosophical heart of the system, from VP of Agentic Security Taesoo Kim: "Disagreement between models is itself a signal: when an auditor flags something as suspect and the debater can't refute it, that finding's posterior credibility goes up." This ensemble-dispute approach is designed to reduce the false-positive rate that makes single-model vulnerability scanning impractical at scale.

MDASH uses different model tiers strategically: SOTA models for reasoning-heavy discovery, distilled models for validation in high-volume passes, and an independent SOTA model for counterpoint — a structure that explicitly prevents the cost of reasoning from bottlenecking the pipeline.

**The May 2026 Patch Tuesday results:** MDASH found 16 vulnerabilities that were included in this month's release. The shortcomings span Windows networking and authentication, including two critical RCE flaws: CVE-2026-33824 and CVE-2026-33823 in the networking stack. Microsoft is also making MDASH available in limited private preview to select customers.

**The strategic context:** This announcement lands less than 48 hours after Google's GTIG report (May 12) documenting the first criminal use of AI to develop a zero-day exploit. The timing may be coincidental, but the framing isn't: the AI vulnerability discovery race is now explicitly two-sided, running in parallel on offense and defense. Microsoft is betting that a 100-agent AI pipeline — operating continuously, at scale, with full codebase access — can find bugs faster than external adversaries who must work from public attack surface only.

For security organizations evaluating AI-assisted vulnerability management: MDASH is the first detailed public architecture of what production-scale AI vuln discovery looks like from a major platform vendor. The model-agnostic design and ensemble-dispute pattern are worth examining as a reference model.

*Sources: [The Hacker News](https://thehackernews.com/2026/05/microsofts-mdash-ai-system-finds-16.html) | [Microsoft Security Blog](https://www.microsoft.com/en-us/security/blog/2026/05/12/defense-at-ai-speed-microsofts-new-multi-model-agentic-security-system-tops-leading-industry-benchmark/)*

### May 2026 Patch Tuesday: 138 Vulnerabilities, Including Windows DNS RCE at CVSS 9.8

**Published:** May 13, 2026

Microsoft's May 2026 Patch Tuesday is among the largest in recent memory: 138 vulnerabilities across its product portfolio, with 30 rated Critical and 104 Important. None were listed as publicly known or actively exploited at time of release — which is itself notable given the volume.

**The headline vulnerability** is CVE-2026-41096 (CVSS 9.8) — a heap-based buffer overflow in the Windows DNS Client that allows an unauthenticated attacker to execute code remotely by sending a specially crafted DNS response. Microsoft's advisory: "the DNS Client incorrectly processes the response and corrupts memory." In certain configurations, no authentication is required and network access is sufficient. The Windows DNS client is present on virtually every Windows system that resolves names on a network.

**Other critical patches:**
- **CVE-2026-42826 (CVSS 10.0)** — Azure DevOps information disclosure, unauthorized attacker, no customer action required (Microsoft has already patched server-side)
- **CVE-2026-33109 (CVSS 9.9)** — Azure Managed Instance for Apache Cassandra: authorized attacker can execute code over the network
- **CVE-2026-42898 (CVSS 9.9)** — Microsoft Dynamics 365 (on-premises): code injection allowing authorized attacker network code execution
- **Netlogon RCE** — Windows authentication stack; specific CVE details in the full advisory

**The AMD side-car:** The update also includes a patch for CVE-2025-54518 (CVSS 7.3), an AMD Zen 2 CPU issue involving improper isolation of shared resources in the operation cache — potentially enabling privilege escalation across privilege levels.

**Patch priority guidance:** CVE-2026-41096 (Windows DNS) should be treated as highest priority for domain-joined and internet-connected Windows systems. The Azure CVEs require no customer action. The Dynamics 365 CVE requires on-premises deployment operators to apply the update manually.

### Two Unpatched Windows Zero-Days: BitLocker Bypass (YellowKey) and CTFMON LPE (GreenPlasma)

**Published:** May 14, 2026

An anonymous researcher operating as "Chaotic Eclipse" / "Nightmare-Eclipse" publicly dropped two new unpatched Windows vulnerabilities this week — a BitLocker bypass and a privilege escalation to SYSTEM — following a prior public disclosure of three Microsoft Defender vulnerabilities from the same researcher.

**YellowKey — BitLocker Bypass via WinRE**

The attack requires physical access (or an existing foothold with USB write capability). Inserting a specially crafted USB drive containing `FsTx` files and rebooting the target into Windows Recovery Environment (WinRE) triggers a shell — with BitLocker unlocked, bypassing the entire encryption protection. The researcher confirmed: "TPM+PIN does not help, the issue is still exploitable regardless."

Security researcher Will Dormann independently reproduced the vulnerability: "Transactional NTFS bits on a USB Drive are able to delete the winpeshl.ini file on ANOTHER DRIVE (X:). And we get a cmd.exe prompt, with BitLocker unlocked." Dormann flagged a secondary concern: the ability for one volume's `\System Volume Information\FsTx` directory to modify another volume's contents "sounds like a vulnerability" independent of the WinRE trigger.

Affected: Windows 11, Windows Server 2022 and 2025. **No patch is available.**

**GreenPlasma — CTFMON Privilege Escalation to SYSTEM**

The Collaborative Translation Framework Monitor (CTFMON) privilege escalation involves a DLL hijacking path through an abandoned COM object registration that allows an attacker with standard user access to obtain a SYSTEM-level shell. The researcher describes it as exploiting "described behaviors" — deliberately designed functionality that creates an unintended privilege path.

Affected: Windows systems with CTFMON active. **No patch is available.**

**Defender posture for both:** Both are publicly disclosed. YellowKey's physical access requirement limits remote exposure but makes it immediately actionable for physical security scenarios (laptop theft, border seizure, targeted intrusion).

### NGINX Rift: 18-Year-Old Heap Buffer Overflow Enables Unauthenticated RCE

**Published:** May 14, 2026

CVE-2026-42945 (CVSS v4: 9.2), codenamed NGINX Rift, is a heap buffer overflow in NGINX's `ngx_http_rewrite_module` that has been present in the codebase since version 0.6.27 — first released in 2008. Eighteen years.

The vulnerability is triggered when an NGINX configuration uses a `rewrite` directive followed by a `rewrite`, `if`, or `set` directive, with an unnamed PCRE capture group (`$1`, `$2`, etc.) and a replacement string containing a question mark (`?`). On such a server, a single crafted HTTP request from an unauthenticated attacker can overflow the heap in the NGINX worker process.

Researcher depthfirst, who discovered and responsibly disclosed the vulnerability on April 21, 2026: "An attacker who can reach a vulnerable NGINX server over HTTP can send a single request that overflows the heap in the worker process and achieves remote code execution. There is no authentication step, no prior access requirement, and no need for an existing session."

On systems with ASLR disabled — common in older enterprise deployments, certain embedded environments, and some containerized configurations — the overflow is attacker-shaped (derived from the request URI), making reliable exploitation significantly more feasible. On ASLR-enabled systems, the attack causes a worker process restart, which is itself a useful availability-layer condition for attackers.

**Affected versions:**
- NGINX Plus R32–R36 → Fixed in R32 P6 and R36 P4
- NGINX Open Source 1.0.0–1.30.0 → Fixed in 1.30.1 and 1.31.0
- Versions 0.6.27–0.9.7: **No fix planned**
- NGINX Instance Manager 2.16.0–2.21.1
- NGINX App Protect WAF 4.9.0–5.8.0
- NGINX Gateway Fabric 1.3.0–2.5.1
- NGINX Ingress Controller 3.5.0–5.4.1

**Exposure assessment:** NGINX is one of the most widely deployed web servers and reverse proxies on the internet. The specific trigger condition (rewrite module with PCRE captures + question mark in replacement) is common in production configurations. Any NGINX server meeting this configuration criteria is potentially vulnerable to an unauthenticated network attacker with HTTP access.

**Immediate action:** Identify NGINX deployments running affected versions, verify whether the rewrite module with PCRE captures is in use, and upgrade. For versions without a planned fix (0.6.27–0.9.7), evaluate configuration-level mitigations or migration.

*Source: [The Hacker News](https://thehackernews.com/2026/05/18-year-old-nginx-rewrite-module-flaw.html) | [depthfirst advisory](https://depthfirst.com/nginx-rift) | [F5 advisory K000161019](https://my.f5.com/manage/s/article/K000161019)*

## 3. Technical Deep Dives

### Android Intrusion Logging: Google and Amnesty Build Spyware Forensics Into the Platform

Google this week unveiled Intrusion Logging for Android — an opt-in feature built into Advanced Protection Mode in collaboration with Amnesty International and Reporters Without Borders. The feature is a direct architectural response to the forensic problem that has plagued high-risk users facing nation-state spyware like Pegasus: by the time a device reaches a forensic investigator, the malware has typically erased its own traces.

**How it works:** Intrusion Logging captures a structured record of device activity on a daily basis — app process starts, installations and uninstalls, network connections (Wi-Fi, Bluetooth, DNS lookups, IP addresses), USB file transfers, system certificate changes, and device lock/unlock events. This record is end-to-end encrypted by the device before transmission, stored on Google servers for 12 months, and keyed to the device owner's screen lock credentials and Google Account password.

The architectural design is critical: Google cannot access the logs. The encryption keys are derived from credentials Google does not hold. This means:
- Malware running on the device cannot access, modify, or delete the logs (they're not local)
- Network-level interception produces only ciphertext
- Government compulsion of Google does not yield plaintext logs
- Only the device owner — with both screen lock credentials and Google Account access — can decrypt

Reporters Without Borders: "The Intrusion Logging function in particular enables detection and forensic analysis of even highly sophisticated and previously difficult-to-detect attacks."

**The policy significance:** The collaboration model — platform vendor working directly with civil-society organizations that have operational experience investigating spyware victims — is itself notable. Amnesty's Security Lab has conducted forensic analysis of Pegasus infections on real victims; that experience shapes what events the logging system captures. This is not a feature designed by security engineers in isolation.

**Limitations to note:** Intrusion Logging is opt-in and requires Advanced Protection Mode enrollment, which also imposes other restrictions (stronger authentication requirements, limits on app sideloading). Once enabled, logs cannot be deleted before the 12-month window expires — even if the account is closed. This is a deliberate design choice to prevent an attacker who gains momentary account access from destroying forensic evidence.

The feature is available now in Android. High-risk users — journalists, activists, lawyers, executives in sensitive sectors — should evaluate enrollment.

*Source: [The Hacker News](https://thehackernews.com/2026/05/android-adds-intrusion-logging-for.html) | [Google Android Security Blog](https://blog.google/security/whats-new-in-android-security-privacy-2026/)*

### GemStuffer: When a Package Registry Becomes a Covert Dead-Drop

The GemStuffer campaign, documented this week by Socket, represents a genuinely novel abuse pattern: using a public package registry not as a malware distribution mechanism, but as a covert data staging and exfiltration infrastructure.

The operation is architecturally simple but analytically interesting. The attacker published more than 150 malicious gems to RubyGems. Each gem, rather than containing malicious installation scripts, contains a scraper: it fetches hard-coded UK local government democratic services portal URLs, packages the HTTP responses as a valid `.gem` archive, and re-publishes the archive to RubyGems using embedded API credentials. Retrieval is a simple `gem fetch` command from anywhere.

Socket's assessment: "The packages do not appear designed for mass developer compromise. Many have little or no download activity, and the payloads are repetitive, noisy, and unusually self-contained." This is not a supply chain poisoning attempt. It's a data dead-drop that happens to be hosted on a trusted public infrastructure.

**Why this matters for defenders:**

The threat model inverted here is worth unpacking. Standard supply chain attacks use the registry's trusted position to distribute malicious code to developers who install it. GemStuffer uses the registry's public accessibility and persistence to store and retrieve exfiltrated data while bypassing conventional DLP.

Consider what typical DLP cannot catch here:
- No malicious payload is downloaded by a victim developer
- No C2 callback from a victim machine to attacker infrastructure
- Outbound traffic is HTTPS to `api.rubygems.org` — an allowed destination in virtually every enterprise environment
- The data is staged publicly, retrievable from any network, without attribution

The UK local government portal data collected includes democratic services content — potentially voter registration data, planning applications, freedom of information records, council meeting minutes. The target selection (specifically government civic portals) suggests either a nation-state or politically motivated actor, or possibly a data-broker operation building a dossier.

RubyGems responded by temporarily suspending new account registration following the campaign. The suspension affects the GemStuffer pattern by removing easy new-account creation, but established compromised accounts with API keys (hardcoded in the gems) remain operational.

**The broader signal:** Any package registry — PyPI, npm, RubyGems, crates.io — can be weaponized as exfiltration infrastructure. Detection requires monitoring outbound package publish events and scanning registry traffic for anomalous publication patterns, not just malicious installs.

## 4. Community Pulse

### Twin IT Contractors Wiped 96 Government Databases in Minutes After Being Fired

The story that led Hacker News Thursday morning is a textbook insider threat case study: Muneeb and Sohaib Akhter, both 34, had been working for a DC-area technology firm that held contracts with 45 federal government clients. On February 18, 2025, both brothers were called into a Microsoft Teams meeting and fired. The call ended at 4:50 PM.

At 4:56 PM, Muneeb — whose account had not been deactivated during the termination call — accessed a US government database his company maintained and began issuing DROP DATABASE commands.

The prosecution documented 96 databases wiped in rapid succession. The brothers had prior convictions (2015 wire fraud and computer fraud charges; Muneeb received three years, Sohaib two), which raises questions about background check processes at a vendor with federal contracts. Muneeb had separately assembled 5,400 stolen credentials from his employer's network data and built Python scripts to credential-stuff commercial sites — including `marriott_checker.py` — successfully booking travel using stolen airline miles.

The HN thread is running over 150 comments. Several key themes: why Muneeb's account wasn't deactivated simultaneously with his brother's (the gap was apparently procedural, not technical), whether federal contractors should face stricter background check requirements, and the general inadequacy of offboarding procedures at organizations where departing employees have database admin access.

**The practitioner takeaway:** Offboarding is a security event, not an HR event. The termination moment — not the end of the business day, not "when IT gets to it" — is when privileged access must be revoked. Systems that require manual ticket submission to revoke database credentials create a window that is predictably, measurably dangerous.

### AI Hallucinations as a Security Vulnerability Class

The Hacker News community is circulating a Keeper Security/THN analysis arguing that AI hallucinations should be treated as a distinct vulnerability class — not just an accuracy problem, but a security risk.

The core finding from the piece: based on Artificial Analysis's AA-Omniscience benchmark evaluating 40 models, all but four models are more likely to produce a confident, incorrect answer than a correct one on difficult questions. In cybersecurity decision-support contexts — where AI outputs drive automated systems, triage decisions, or patch prioritization — a confident hallucination can be more dangerous than an obvious error.

The operational scenarios where this matters: hallucinated CVE severity scores driving patch deprioritization, AI-generated incident reports citing nonexistent indicators of compromise, threat intelligence hallucinations redirecting investigative resources, and AI-assisted vulnerability management tools flagging phantom issues while missing real ones.

The framing the community is debating: should hallucination-prone AI security tooling require the same kind of disclosure as other probabilistic security tools? Is confident-wrong output a defect that vendors have an obligation to characterize? Several practitioners in the thread note they've seen hallucinated CVE data cited in actual vulnerability management workflows — the problem is no longer theoretical.

*Source: [The Hacker News / Keeper Security](https://thehackernews.com/2026/05/how-ai-hallucinations-are-creating-real.html)*

## 6. Five Things to Take Into the Rest of the Day

**1. The AI framework CVE window is now measured in hours.** Sysdig's data across PraisonAI, Langflow, LMDeploy, and Marimo establishes a consistent pattern: agentic AI tooling CVEs are being scanned within hours of advisory publication. If you operate or deploy open-source AI frameworks on internet-accessible infrastructure, your patch deployment window is no longer days — it's the same morning the advisory drops.

**2. MDASH shows what defensive AI vuln discovery looks like at scale.** Microsoft's 100-agent, auditor-debater pipeline found 16 Patch Tuesday vulnerabilities before attackers did. The ensemble-dispute model — where disagreement between agents is treated as a positive signal — is the core architectural insight. Organizations building internal red team tooling should study this design.

**3. NGINX Rift is an 18-year-old RCE. Check your configurations today.** The trigger condition (rewrite module + PCRE unnamed capture + question mark in replacement string) is present in many standard proxy configurations. This is not an exotic edge case. Run `nginx -T | grep -A2 rewrite` on your servers and verify your version is patched.

**4. Offboarding is a security event. The termination call is the trigger.** The Akhter brothers case is not unique — it's a well-documented pattern. The moment a privileged employee is terminated is the moment their database credentials, VPN access, and cloud IAM permissions must be revoked, not when IT processes the ticket. If your offboarding process involves any manual queue, that queue is your exposure window.

**5. Android Intrusion Logging is worth deploying for your highest-risk users now.** If you have employees or clients who face elevated spyware threat — executives, legal, M&A teams, journalists, anyone who has received targeted phishing from nation-state actors — Advanced Protection Mode with Intrusion Logging enabled provides forensic capability that did not exist at the platform level six months ago.
