### Trump Signs AI Executive Order: Voluntary 30-Day Model Vetting, NSA Benchmarks, and a Federal Cybersecurity Clearinghouse

On June 2, President Donald Trump signed **"Promoting Advanced Artificial Intelligence Innovation and Security,"** an executive order that marks the most significant federal AI security policy action since the previous administration's framework was rescinded. The order pairs a light-touch governance philosophy with concrete federal cybersecurity directives that will reshape how AI models are evaluated before deployment.

**What the Order Does:**

The EO is organized around four principal actions, each with a 30- to 60-day implementation deadline:

1. **AI Cybersecurity Clearinghouse** — The Treasury Secretary, in consultation with the National Cyber Director, NSA, and CISA, must establish an industry-collaborative clearinghouse within 30 days. Its mandate: coordinate and deconflict vulnerability scanning, discover and validate software flaws, and prioritize remediation and patch distribution. This directly addresses the fragmentation problem that Anthropic's Project Glasswing exposed — multiple organizations scanning the same codebases independently, wasting researcher effort and overwhelming maintainers.

2. **Classified Frontier Model Benchmarking** — The NSA Director, with Treasury, CISA, NIST, and the White House science advisor, will develop a classified benchmarking process within 60 days to assess the advanced cyber capabilities of AI models and determine the threshold at which a model becomes a "covered frontier model." This is a dual-use assessment framework — designed to identify when a model's cyber-offensive capability crosses a national security concern threshold.

3. **Voluntary 30-Day Pre-Release Vetting** — AI developers can voluntarily submit new models for federal cybersecurity review up to 30 days before public release. **[The New York Times](https://www.nytimes.com/2026/06/02/technology/trump-executive-order-ai.html)** reported that the window is voluntary — developers choose to submit — but once submitted, the review period runs up to 30 days. The order explicitly avoids mandatory registration or pre-deployment licensing, drawing a line between the current administration's approach and the more prescriptive frameworks proposed in Europe and California.

4. **Federal System Hardening** — CISA must release Binding Operational Directives to prioritize civilian federal cyber defense, expand AI-enabled defensive tooling programs, and facilitate access to frontier models for agencies, state/local authorities, and critical infrastructure operators like rural hospitals, community banks, and local utilities.

**Industry Reaction:**

OpenAI CEO Sam Altman said the order "gets the balance right," praising the voluntary framework and focus on getting cyber tools to defenders. The order's reception reflects its carefully negotiated positioning: industry-friendly compared to California's SB 1047 or the EU AI Act, but doing substantially more than the prior administration's framework in directing federal cyber resources toward AI vulnerability management.

**[Politico](https://www.politico.com/news/2026/06/02/trump-signs-downsized-ai-order-00946389)** reported that the order went through "weeks of reversals" before signing, with internal debates over mandatory versus voluntary testing, the role of the NSA in civilian AI governance, and whether the clearinghouse should have enforcement authority. The final version reflects a deliberate narrowing: voluntary model submission rather than mandatory testing, clearinghouse collaboration rather than oversight, and classified benchmarks rather than public standards.

**Why It Matters:**

The EO's practical significance for security teams is threefold. First, **the AI Cybersecurity Clearinghouse formalizes the vulnerability coordination problem** that Project Glasswing demonstrated at scale — when AI can find 10,000+ critical vulnerabilities in a month, the industry needs a deconfliction mechanism to prevent hundreds of simultaneous disclosures overwhelming every maintainer. Second, **the classified benchmarking process means that "model security" now has a national security classification tier** — organizations deploying frontier models in critical infrastructure contexts will need to account for national security-level assessment requirements. Third, **CISA's Binding Operational Directives will translate the EO into enforceable requirements for federal contractors** within months, meaning the order's effects will propagate through federal procurement before the year is out.

## 2. Breaking News

### VS Code Zero-Day: One Click to Steal All Your GitHub Tokens

A security researcher has released exploit code for a Visual Studio Code zero-day vulnerability that allows attackers to steal GitHub authentication tokens by tricking users into clicking a single link. **[BleepingComputer](https://www.bleepingcomputer.com/news/security/vs-code-zero-day-lets-hackers-steal-github-tokens-in-one-click/)** reported on June 3 that the flaw — documented by researcher Ammar Askar — abuses VS Code's sandboxed webview message-passing system in github.dev (the browser-based VS Code for GitHub repositories).

**The Attack Chain:**

- When a user clicks a malicious link, github.dev loads POSTed OAuth tokens that allow the browser-based editor to interact with GitHub on the victim's behalf.
- Malicious JavaScript running inside a webview exploits the message-passing system to simulate keypresses in the main editor.
- The simulated keypresses install a malicious VS Code extension that extracts the GitHub OAuth token and queries the GitHub API to enumerate all repositories the victim can access.
- Critically, the token is not scoped to the particular repository the victim interacted with — it has full access to every repository the user can access.

**Why Public Disclosure:**

Askar published the exploit immediately, with one hour's notice to GitHub. His rationale, documented in the **[blog post](http://blog.ammaraskar.com/github-token-stealing/)** and a concurrent **[Reddit thread](https://www.reddit.com/r/netsec/comments/1tuue57/1click_github_token_stealing_via_a_vscode_bug/),** stems from a prior negative experience with Microsoft's Security Response Center (MSRC) in which a previously reported VS Code bug was silently fixed without credit or acknowledgment of the security impact.

**Mitigation:**

Until Microsoft patches the vulnerability, users can protect themselves by clearing cookies and local site data for github.dev in their browser. This ensures the "The extension 'GitHub Repositories' wants to sign in using GitHub" warning appears when clicking on exploit links, giving users a chance to refuse authentication.

**Why It Matters:**

This is not an esoteric bug. github.dev is a widely used surface for interacting with GitHub repositories — developers click links to it daily from PR comments, issue discussions, and repository READMEs. The one-click exploitation profile means **any developer who clicks a link from a GitHub issue, pull request comment, or even a third-party website is potentially exposed to token theft.** The attack surface extends to every organization that uses GitHub for code hosting, CI/CD, and project management — which is to say, nearly every software team.

### jqwik 1.10.0: The First Open-Source "Protestware" Prompt Injection

On May 25, the maintainer of **jqwik** (a Java property-based testing library) released version 1.10.0 to Maven Central containing a hidden instruction targeting AI coding agents. The payload told agents to disregard previous instructions and delete all jqwik tests and code. The instruction was hidden from human eyes using ANSI terminal escape codes but fully readable in raw CI logs, build output, and any stream that captures bytes literally.

**[Snyk](https://snyk.io/blog/protestware-open-source-maintainer-qwik-1-10-0-prompt-injection/)** analyzed the attack on June 2. The mechanism was straightforward: the malicious method `printMessageForCodingAgents()` printed the instruction, then emitted `ESC [2K` (erase entire line) followed by a carriage return twice. On a real terminal, the message flashes and disappears. In Jenkins logs, GitHub Actions output, and agent-wrapped subprocesses, the instruction sits in plain text — exactly where an AI coding agent parsing its own output stream would read it.

**Timeline:**

- **May 25:** Version 1.10.0 lands on Maven Central. Release notes say nothing.
- **May 27:** Developer rbatllet spots odd CI log output, decompiles the JAR, finds the `print` calls. Issues filed against jqwik and Claude Code repos.
- **Late May:** Maintainer Johannes Link updates release notes to admit the injection, says jqwik should not be used by AI agents.
- **Shortly after:** Version 1.10.1 ships. The directive is softened and the hiding becomes opt-in.

**Why It's a Supply Chain Problem:**

This is the first documented case of a maintainer using prompt injection as a **supply chain weapon**. Nothing was compromised in the usual sense — no stolen credentials, no sandbox escape, no account hijack. But the dependency chain trusted the package distribution mechanism, and the payload was delivered through that trust.

The asymmetry is the game: invisible to a human watching a terminal, fully legible to a machine parsing the log. Any pipeline that pulled the dependency, ran tests, and fed output back into an LLM agent — Claude Code, Copilot agent mode, Cursor — could have triggered the injection. One major agent caught it and refused to act. But the pattern is now public, and copying it requires nothing more than access to a popular package registry and knowledge of the ANSI escape sequence.

**Why It Matters:**

The jqwik incident establishes a **new vulnerability class: supply chain prompt injection via package output.** Any popular library whose test output is processed by AI coding agents is now a potential vector. Teams using AI coding agents in their development workflows should audit whether their dependency pipeline feeds raw test output back into agent context, and whether they trust every upstream maintainer to not weaponize their own packages.

### Google Rolls Out "Fake Call Detection" — Platform-Level AI Voice Deepfake Defense

Google is introducing a new Android security feature called **fake call detection** that will automatically detect and flag phone calls where scammers use AI voice-cloning to impersonate a user's personal contacts. **[BleepingComputer](https://www.bleepingcomputer.com/news/security/google-adds-android-protection-against-ai-deepfake-scam-calls/)** reported on June 3 that the feature rolls out globally this month to Android 12 and later devices, starting with Pixel devices, and is enabled by default.

**How It Works:**

- When a legitimate contact places a call, their device sends a silent, encrypted confirmation signal (via RCS) to the recipient's device in real time.
- If that signal is missing — indicating the call may be spoofed — the recipient's device pings the contact's actual phone to verify the call's authenticity.
- If the contact's device confirms it is not placing a call, the recipient receives an on-screen warning to hang up immediately.

The feature addresses the combination of two widespread fraud tactics: **number spoofing** (making a call appear to come from a familiar contact) and **AI voice-cloning** (mimicking that person's voice in real time). Google's announcement notes that impersonation scams caused $2.95 billion in reported losses in 2024 in the U.S. alone, with INTERPOL's March 2026 Global Financial Fraud Threat Assessment flagging impersonation fraud as contributing to more than $440 billion in global losses.

**Why It Matters:**

This is a significant step toward making AI deepfake defense a **platform-level capability rather than a third-party app feature**. By building the verification into the dialer itself, using the RCS standard, and enabling it by default, Google addresses the adoption problem that plagues standalone anti-scam apps. The architecture — out-of-band verification via a different channel than the call itself — is the correct design pattern for defeating deepfake impersonation at scale.

For enterprise security teams, the signal is clear: platform vendors are beginning to treat AI voice impersonation as a systemic threat warranting OS-level defenses. Organizations should evaluate whether their corporate device management policies support or conflict with this feature.

*Sources: [BleepingComputer](https://www.bleepingcomputer.com/news/security/google-adds-android-protection-against-ai-deepfake-scam-calls/) | [Google](https://blog.google/products/android/android-fake-call-detection/)*

### Microsoft Build 2026: Windows Goes Agent-Native with Hardened Sandboxes and AI Governance

At **[Microsoft Build 2026](https://build.microsoft.com/en-US/home)** on June 2, Microsoft announced a sweeping vision for Windows as an **agent-native operating system**, with AI agents treated as first-class platform citizens secured through OS-level runtime isolation, identity management, and policy-based governance.

**Key Security Announcements:**

- **Windows Agent Platform (WAP)** — A new set of OS-level services providing a dedicated runtime for agents in any language. Agents run inside isolated sandboxes backed by Pluton security processor and virtualization-based security. An agent that tries to read a file outside its allowed scope hits an invisible wall, and the OS logs the attempt for auditing.
- **Microsoft Execution Containers (MXC) SDK** — Session isolation paired with per-agent unique local IDs for precise control, least-privilege access, and full auditability. Access policies can be applied via Windows session isolation with lifecycle governance through Microsoft Entra and Intune.
- **Agent 365 Integration** — Native Intune integration to set policies that gate agent runtime execution and control how agents run. Targeted at IT teams who need to balance deploying agents at scale with managing risk. Policy controls can dictate which agents can run, which data they can access, and under what conditions they must pause for human approval.
- **Microsoft IQ** — A mysterious new intelligence layer described as a "policy-as-code engine combined with a reasoning model that understands corporate rules." During demos, IQ checked agent-drafted emails against compliance standards, ensured database queries didn't expose PII, and demanded multi-factor approval for fund transfers.

**[The Windows Developer Blog](https://blogs.windows.com/windowsdeveloper/2026/06/02/windows-platform-security-for-ai-agents/)** emphasized that containment bounds what agents can access and do, so non-deterministic behavior doesn't translate into uncontrollable risk — a fundamental architectural shift from the app-security model that has defined Windows for decades.

**Why It Matters:**

Microsoft's Build 2026 announcements represent the most significant platform-level agent security investment yet from any operating system vendor. The architectural approach — **containment, identity, and manageability as foundational OS primitives** — is the correct one. Agent security cannot be bolted on as an application-layer concern when agents operate with file system, network, and credential access that rivals or exceeds human user privileges.

For enterprise security teams, the practical takeaway is that **Windows will soon have enforceable agent governance baked in**. Organizations should be evaluating now whether their agent deployments will run on Windows, what policies they would apply through Intune, and whether their data classification labels (Power BI, Purview, Priva) already define the boundaries their agents should respect.

## 3. Technical Deep Dives

### Microsoft MDASH: 100+ Specialized AI Agents Running the Security Scanning Pipeline

Among the many announcements at Build 2026, one deserves dedicated attention from security practitioners: **MDASH** (Microsoft Security multi-model agentic scanning harness), an expanded preview of which was detailed in **[Microsoft's security blog](https://www.microsoft.com/en-us/security/blog/2026/06/02/microsoft-build-2026-securing-code-agents-and-models-across-the-development-lifecycle/)** .

**What MDASH Does:**

MDASH orchestrates a pipeline of **more than 100 specialized AI agents** using an **ensemble of models** to discover, validate, and prove exploitability across codebases written in popular programming languages. The system uses a "configurable panel of models" ranging from state-of-the-art (SOTA) heavy reasoners to cost-effective models for high-volume operations — trading speed, recall, and cost while minimizing dependency on any single model.

**The Architecture That Matters:**

The strategic insight behind MDASH is not that one model is better than another at finding vulnerabilities. It's that **the agentic system around the model is the durable advantage**, not the model itself. MDASH combines:

- **Multi-model orchestration** — A pipeline architecture where different models handle different stages of vulnerability discovery: reconnaissance via cost-effective models, deep analysis via reasoning models, exploit validation via specialized models.
- **Over 100 trillion signals per day** — Microsoft's security signal volume fed into the detection pipeline, correlating vulnerability findings with telemetry about real-world exploit attempts.
- **CyberGym benchmark: 96.55%** — The system recently jumped roughly 10% in less than three weeks to this score, demonstrating that multi-model agentic systems improve substantially faster than single-model approaches on vulnerability discovery tasks.

**Integration with Microsoft Defender and GitHub Code Security:**

MDASH now has native integration with Microsoft Defender and GitHub Code Security (part of the former GitHub Advanced Security suite). This means vulnerability findings from the agentic pipeline flow directly into the tools that developers and security teams already use — closing the loop from discovery to remediation without requiring a new platform.

**Why It Matters:**

MDASH's architecture represents a direct answer to the challenge Anthropic's Mythos Glasswing results exposed: **vulnerability discovery velocity has outpaced remediation velocity, and the solution must be agentic, not just better models.** MDASH is not trying to build a single model that finds every bug — it's building a system that coordinates 100+ agents across models, guided by telemetry and validated against exploitability criteria.

For enterprise security teams evaluating AI vulnerability discovery tools, MDASH's multi-model orchestration approach is the architectural pattern to watch. The rest of the industry is still debating whether a single model can find vulnerabilities reliably. MDASH's assumption is that no single model will ever be sufficient, and the system must be built to route work to the right model for each task.

### Mullvad: Age Verification as the End of a Free Internet?

**[Mullvad VPN's blog post](https://mullvad.net/en/blog/age-verification-for-social-media-the-beginning-of-the-end-for-a-free-internet)** on the implications of mandatory social media age verification reached 527 points and 433 comments on Hacker News — the second most popular story of the day.

The privacy and data-security implications are substantial — every age-verification system becomes a honeypot for identity theft, and every platform that implements age verification expands its data collection surface.

For AI security practitioners, the post raises a parallel concern: as AI agents become indistinguishable from humans in online interactions, platforms will be increasingly pressured to implement **proof-of-personhood** systems that can distinguish human users from AI agents. Age verification is a specific instance of a broader trend toward identity-proving requirements that will shape the agent security landscape.

## 6. Five Things to Take Into the Rest of the Day

1. **The AI executive order changes the compliance timeline for federal contractors.** The AI Cybersecurity Clearinghouse and CISA Binding Operational Directives will translate the EO into enforceable requirements within months. If your organization handles federal data or operates critical infrastructure, start assessing how the clearinghouse's vulnerability coordination and the classified frontier model benchmarks will affect your procurement and compliance obligations. The voluntary model review window is optional for model developers, but the downstream security requirements for federal contractors are not.

2. **VS Code's github.dev surface is a one-click token theft vector. Audit your developer workflows today.** The github.dev OAuth token theft zero-day demonstrates that browser-based development tools inherit the security properties of web applications — and web applications have click-based exploitation. Every developer in your organization who has used github.dev is potentially exposed. Clear github.dev site data, enforce Conditional Access policies for GitHub OAuth flows, and evaluate whether browser-based VS Code should be allowed in your environment pending Microsoft's patch.

3. **Supply chain prompt injection is now a demonstrated attack class. Audit your CI pipeline for tool-output-to-agent-context flows.** The jqwik protestware proves that any popular library whose test output is consumed by an AI coding agent is a potential vector. The attack requires no account compromise — only a maintainer willing to weaponize their own package, and a pipeline that feeds raw output into agent context. Review whether your CI/CD pipeline hands terminal output directly to Claude Code, Copilot, or Cursor. If it does, the trust model of every dependency in your graph just became a security surface.

4. **Platform-level AI agent governance is arriving in Windows. Evaluate your Intune policies now.** Microsoft's Build 2026 announcements make it clear that within the next OS release cycle, Windows will have enforceable agent governance built into the platform via MXC containers, Microsoft IQ, and Agent 365 policies. Organizations should start mapping their data classification labels (Purview, Priva, Power BI) to agent access policies now — because when the platform supports policy-based governance, the bottleneck will be the policy definitions, not the enforcement mechanism.

5. **AI-powered deepfake scams are now being fought at the OS level. Platform defenses matter more than app-level ones.** Google's fake call detection, rolling out to Android 12+ this month, is the first major OS-level AI deepfake defense. The architecture — out-of-band verification via RCS rather than in-band via the voice channel — is the correct design pattern. For organizations providing mobile devices, evaluate whether this feature is supported on your fleet and whether corporate MDM policies should explicitly configure or allow it. The $2.95 billion in U.S. impersonation scam losses in 2024 justifies the investment.
