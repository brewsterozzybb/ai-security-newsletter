## 1. Headliners

### ChatGPT for Google Sheets Exfiltrates Workbooks — OpenAI Disables Apps Script After PromptArmor Disclosure

**[PromptArmor](https://www.promptarmor.com/resources/gpt-for-google-sheets-data-exfiltration)** published a disclosure on June 1 documenting a critical vulnerability in ChatGPT's Google Sheets extension — installed over 185,000 times since its launch less than a month ago — that allows a single indirect prompt injection to exfiltrate data across the victim's entire Google Sheets account.

**The Attack Chain:**

1. A user works on an internal financial model in Google Sheets.
2. They import an external dataset to use in their model.
3. The external sheet has a prompt injection hidden in white text — invisible to the human eye but fully readable by ChatGPT's sidebar agent.
4. The user asks ChatGPT for help integrating the data.
5. The injection manipulates ChatGPT to run an attacker-controlled external Google Apps Script.

Once the script executes, the consequences are multi-pronged: **exfiltration of up to 12 workbooks** from across the victim's account, display of an interactive **phishing pop-up** rendered inside Google Sheets, overwriting the **entire GPT sidebar** with an attacker-controlled chatbot interface, and attacker-controlled edits to workbooks.

Critically, this attack bypasses the "Apply edits automatically" setting that users explicitly enable for approval-based protection. The Apps Script runs with the permissions the user granted to the ChatGPT extension, and the injection uses those permissions without asking again.

**OpenAI's Response:**

OpenAI told PromptArmor: "We've taken immediate steps to protect users against potential attacks in this area by removing the model's ability to generate Apps Script code, which should eliminate the risk to users of ChatGPT for Google Sheets."

The company also committed to "re-evaluating our sandboxing approach" and conducting "a re-review of similar functionality in other surfaces." The disclosure timeline is notable: PromptArmor says OpenAI did not respond to initial disclosure emails, and the vulnerability was only addressed after public publication.

**Why It Matters:**

This is the second major AI-platform-plugin vulnerability this week (ChatGPhish on May 30, now this on June 1), and the pattern is consistent: **every surface where AI can read external content and act on behalf of a user is a systemic trust boundary failure.** The architecture treats any data the model reads as safe input, and the plugin permission model grants capabilities (execute scripts, read workbook contents) that the model can be manipulated into using against its user.

For enterprise security teams, this means that ChatGPT's Excel/Google Sheets extensions, Copilot in Office, Claude's Doc reader, and every similar productivity-AI integration represent an undefended perimeter. The features are deployed ahead of the sandboxing, and the sandboxing is reactive — deployed after the incident, not before.

## 2. Breaking News

### OWASP Classifies Memory Poisoning as ASI06 — The Persistent Attack Surface That Changes the Defense Model

**[Help Net Security](https://www.helpnetsecurity.com/2026/06/01/owasp-agent-memory-guard/)** covered the release of the **OWASP Agent Memory Guard** project, which formalizes **Memory Poisoning (ASI06)** in the OWASP Top 10 for Agentic Applications. This is not an incremental update — it represents a structural shift in how the security community understands AI agent threats.

**The Three-Phase Lifecycle:**

Memory poisoning operates across three distinct phases:

1. **Injection** — A malicious instruction enters via an external data source the agent processes: a compromised PDF, a manipulated inbound email, a poisoned knowledge-base article, or a hidden spreadsheet cell.
2. **Persistence** — The instruction is written to the agent's long-term semantic memory, where it blends into the "learned" behavioral profile, indistinguishable from legitimate training data.
3. **Execution** — Weeks or months later, the agent retrieves the poisoned memory as trusted historical context, triggering data exfiltration, unaligned behavior, or unauthorized tool invocation.

The structural property that distinguishes this from prompt injection is **the time gap**. Stateless prompt injection is detected in the same session it's delivered — there's still an active reference frame against which to validate the attack. Memory poisoning's payload is compressed, translated, and embedded deeply into the retrieval store before it ever fires. By the time the agent acts on it, the malicious instruction has gained what researchers call "the credibility of memory itself."

**The Defense Substrate Must Move into the Memory Layer:**

Existing defenses don't transfer. Input sanitization happens upstream of the memory write. Output validation happens downstream of the retrieval. Memory poisoning bypasses both by writing past the prompt layer entirely.

The Agent Memory Guard project defines four defense phases:

- **Ingest** — Scan and filter content before memory writes.
- **Classify** — Identify and quarantine potentially poisoned memory segments.
- **Retrieve** — Apply trust scoring to retrieved context before it reaches the agent.
- **Respond** — Validate agent actions against poisoned memory before execution.

**Why It Matters for Monday Morning:**

This formalization confirms what practitioners have been warning about: memory is the new attack surface, and the defenses that worked for prompt injection don't transfer. Any organization running AI agents that maintain persistent memory — which is virtually every production agent deployment — now has a clearly defined vulnerability class with a named defense framework. The OWASP classification means that compliance frameworks (SOC 2, ISO 42001, EU AI Act) will likely reference ASI06 in their next revision cycles. Teams should evaluate whether their agent deployments have any memory-layer defenses at all.

*Sources: [Help Net Security](https://www.helpnetsecurity.com/2026/06/01/owasp-agent-memory-guard/) | [LLMS3 — When Memory Became the Attack Surface](https://llms3.com/blog/when-memory-became-the-attack-surface-may-2026) | [OWASP Agent Memory Guard](https://owasp.org/www-project-agent-memory-guard/)*

## 3. Technical Deep Dives

### Anthropic Publishes "Zero Trust for AI Agents" — A Concrete Taxonomy for Agent Threat Modeling

On May 27, **[Anthropic](https://www.anthropic.com)** published a whitepaper titled **"Zero Trust for AI Agents"** that systematically defines a security framework for enterprise AI agent deployment, covered by **[VendorDeep](https://www.vendordeep.com/report/anthropic-publishes-zero-trust-agents)** and referenced across the security community this week.

**Three Core Principles:**

The framework adapts zero-trust architecture's canonical principles to the agent context:

1. **Never trust, always verify** — Every agent action, even within an authenticated session, is independently validated against policy.
2. **Assume breach** — Design agent systems such that a compromised agent cannot compromise the broader environment.
3. **Least privilege** — Agents operate with the minimum permissions necessary for their function, and those permissions are scoped per-action, not per-session.

**Five Agent-Specific Threats:**

Anthropic identifies five threat categories that map to real incidents and disclosures covered in this newsletter over the past week:

- **Prompt Injection** — Microsoft Research confirms that LLMs cannot reliably distinguish informational context from executable instructions. This is an architectural limitation, not a bug.
- **Tool Poisoning** — The first wild malicious MCP server has been discovered and documented. MCP tool descriptions, the free-form text that tells the model what a tool does, are part of the prompt context and can be weaponized.
- **Identity and Privilege Abuse** — The confused deputy problem for AI agents, compounded by memory-cached credentials that enable cross-session privilege escalation.
- **Memory/Context Poisoning** — Maps directly to OWASP ASI06 above.
- **Supply Chain Attacks** — Malicious MCP servers, poisoned packages, and compromised agent frameworks.

**Why It Matters:**

Anthropic's whitepaper is significant for the same reason the OpenAI Frontier Governance Framework was significant last week: it provides a reference architecture that defenders can use to structure their programs. The five threat categories give CISOs a taxonomy they can use in risk assessments, vendor evaluations, and policy documents. And the zero-trust framing — trust nothing an agent says, verify everything an agent does — is the correct architectural model for an era where agents are being deployed far faster than their security properties are understood.

The practical implication: if your agent security program doesn't have categories for tool poisoning and supply chain attacks, it is incomplete. If your agents don't operate under least privilege, they are operating with excessive agency.

### The Zero-Day Clock: AI Has Collapsed the Vulnerability-to-Exploit Timeline

An article by **[Tom's Hardware](https://www.tomshardware.com/tech-industry/cyber-security/zero-day-clock-visualizes-and-quantifies-the-effects-of-ai-on-software-security-time-until-exploit-went-from-one-year-to-one-day-and-projected-to-be-one-minute-soon-enough)** this week covered the **Zero-Day Clock** project — a visualization of how AI-powered vulnerability discovery and exploit generation is collapsing the window between disclosure and exploitation.

**The Numbers:**

| Era | Time-to-Exploit |
|---|---|
| Pre-AI (traditional) | ~1 year |
| Current AI-assisted | ~1 day |
| Projected near-term | ~1 minute |

The Zero-Day Clock project argues that the traditional 90-day vulnerability disclosure window — the industry standard negotiated between researchers and vendors — is effectively dead. If AI can find a vulnerability and generate a working exploit in hours, a 90-day patch cycle leaves systems exposed for three months to an exploit that costs near-zero to produce.

The article notes that the Model Context Protocol (MCP) ecosystem is particularly vulnerable to this collapse, given the 40+ CVEs already disclosed against MCP implementations in 2026 and the protocol's minimal built-in authentication and access controls.

For enterprise defenders, the clock's argument maps directly onto the practical problem the industry now faces: vulnerability discovery velocity has accelerated, but remediation velocity has not. The Zero-Day Clock isn't just a visualization — it's a warning that patch management as practiced today is structurally inadequate for the AI era.

## 4. Community Pulse

### Gartner: Uniform AI Agent Governance Will Cause Enterprise Failure

**[Gartner](https://www.gartner.com/en/newsroom/press-releases/2026-05-26-gartner-says-applying-uniform-governance-across-ai-agents-will-lead-to-enterprise-ai-agent-failure)** published a press release on May 26 with a pointed warning: applying uniform governance to all AI agents, regardless of their autonomy level and scope, will lead to enterprise AI agent failure.

The insight is deceptively simple but operationally important. A read-only summarization agent that operates on internal documents faces a fundamentally different risk profile than a write-capable agent that executes financial transactions across external APIs. Applying the same governance controls to both means either under-governing the high-risk agent or over-governing the low-risk one — and either outcome is failure.

Gartner's framing directly supports the tiered governance approach that Microsoft's Agent Governance Toolkit and Okta's agent directory both enable. The architectural pattern is converging: **agent governance must be risk-tiered, identity-based, and differentiated by autonomy level.**

For security teams building agent governance programs, the Gartner warning provides a convenient framing to use in board conversations: "The AI agents running your quarterly close cannot be governed the same way as the one summarizing your Slack threads — and applying the same rules to both will break either security or productivity."

## 6. Five Things to Take Into the Rest of the Day

1. **Audit every AI productivity plugin your organization uses — the trust model is the vulnerability.** The ChatGPT for Google Sheets disclosure demonstrates that AI extensions with read/write access to enterprise data represent a systemic trust boundary failure. Any plugin that can read user content and execute privileged actions (Apps Script, macros, API calls) is a vector waiting for a prompt injection. Inventorize what extensions are deployed, what permissions they hold, and whether they have third-party code generation capabilities.

2. **Memory poisoning is now a named vulnerability class with a defense framework. Build your defense.** OWASP's formalization of ASI06 means that agent memory security is moving from "emerging threat" to "compliance requirement." Evaluate whether your agent deployments have any of the four defense phases (ingest, classify, retrieve, respond) operationalized. If your agents keep memory and you cannot audit what is in that memory, you have an unmanaged attack surface.

3. **Differential agent governance is the correct architectural pattern.** Gartner's warning about uniform governance failing maps directly to the practical challenge: a read-only summarization agent and a write-capable financial transaction agent must have different governance tiers. If your agent policy is one-size-fits-all, you are either blocking productivity or exposing risk. Start tiering by autonomy level and scope.

4. **Zero-trust for agents is not optional — it is the only viable architecture.** Anthropic's whitepaper provides the taxonomy for threat modeling (five categories: prompt injection, tool poisoning, identity abuse, memory poisoning, supply chain). Use it. If you can't name which of these threats your agent deployment is exposed to, you cannot defend against them.

5. **The vulnerability-to-exploit window is collapsing toward zero. Your patch velocity needs to match.** The Zero-Day Clock's projection of one-minute exploit generation is not alarmism — it's the logical conclusion of AI-powered vulnerability discovery that already shortened the window from one year to one day. If your organization's mean-time-to-patch for critical vulnerabilities is measured in weeks, that timeline is now measured in unacceptable risk. Invest in automated patch deployment and architectural defenses that buy time.
