### Ruflo CVE-2026-59726: CVSS 10.0 Zero-Authentication RCE in MCP Bridge of 67K-Star AI Agent Platform — 233 Tools Exposed, Default `docker-compose up` Binds to 0.0.0.0, Patched in 3.16.3

**Noma Labs** disclosed on **July 29, 2026** (with **SecurityWeek**, **The Hacker News**, **Help Net Security**, and **Rescana** confirming within hours) a **CVSS 10.0** vulnerability in **Ruflo** (formerly Claude Flow), the open-source AI agent orchestration platform with **67,000+ GitHub stars**, ranked **#2 on MCPMarket**, and shipped with approximately **10 million downloads and 1 million active users**. Tracked as **CVE-2026-59726** and nicknamed **RufRoot** by Noma, the vulnerability is in Ruflo's **MCP Bridge** — the Express.js server that handles all tool invocations. The bridge exposes **233 tools** covering shell access, database operations, agent management, and memory storage on **port 3001 with zero authentication**. The default `ruflo/docker-compose.yml` binds port 3001 to **0.0.0.0**, exposing every network-reachable instance to unauthenticated exploitation. The patch is in **Ruflo 3.16.3**.

**The single-request exploit chain.** Per Noma's technical writeup, Ruflo's `POST /mcp` endpoint implements the MCP JSON-RPC protocol and passes tool invocations directly to `executeTool()` with no authentication layer. A command blocklist (`AUTOPILOT_BLOCKED_PATTERNS`) exists, but it "applies only within the autopilot flow. The `/mcp` endpoint bypasses it completely." Among the 233 exposed tools is `ruflo__terminal_execute`, which runs arbitrary shell commands inside the container. The full exploit is one HTTP request: `curl -s -X POST https://<target>:3001/mcp -H "Content-Type: application/json" -d '{"jsonrpc":"2.0","id":1,"method":"tools/call","params":{"name":"ruflo__terminal_execute","arguments":{"command":"id && hostname"}}}'`. The command runs as the container's `node` user (UID 1000), and that is sufficient for full compromise because credentials, agent APIs, memory stores, and the database are all accessible from inside the container without further escalation.

**From shell to rogue agent swarm.** Per SecurityWeek's coverage, successful exploitation enables **six attack vectors**: (1) **reconnaissance** via the exposed MCP tool inventory, (2) **remote code execution** via `ruflo__terminal_execute`, (3) **API key and conversation theft** by reading provider credentials from the container environment, (4) **spawning attacker-controlled agent swarms** on the victim's keys, (5) **poisoning the AgentDB learning store** to influence AI outputs for all users, and (6) **deploying persistent backdoors** while clearing shell history to remove traces. The poisoning vector is the operationally significant one: a single write to the AgentDB learning store causes every subsequent agent in the swarm to use the attacker's preferred behavior, and the contamination is silent because the AgentDB writes are normal user-facing operations from the platform's own perspective.

**The "MCP Bridge as central nervous system" framing.** Per Noma, "The MCP Bridge isn't a random auxiliary debug interface; rather, it is Ruflo's central nervous system. Every tool call, every agent action, every memory operation goes through the MCP bridge. Mistakenly giving unauthenticated access to the MCP Bridge means giving unauthenticated access to everything." Per Ruflo's advisory (linked from SecurityWeek), "in default docker-compose deployments the bridge and MongoDB were bound to all interfaces." The framing is the same one the **Hugging Face customer-controlled sandbox boundary** (covered Jul 29) and the **Azure DevOps MCP confused-deputy** (covered Jul 28) make from different angles: a single management surface becomes the full attack surface, and the procurement consequence is the same one the **MCP 2026-07-28 final spec** (covered Jul 29) and the **CREST AI-Enabled Pentesting Accreditation** (covered Jul 28) make: every MCP-server deployment now needs an explicit "is the MCP server bound to all interfaces by default" question, and the answer has to be in writing.

**Why it matters:** First CVSS 10.0 in the MCP ecosystem, on a platform with 67K GitHub stars and 10M downloads, in a vulnerability class (default-bind-to-all-interfaces) that is structurally identical to the **JFrog Artifactory 8-CVE chain** (covered Jul 29) and the **n8n fourth-sandbox-escape** (covered Jul 28) — three high-profile agent-platform CVEs in three days, all rooted in the same "internal management surface exposed externally" failure mode. For enterprise security teams: (1) inventory every Ruflo deployment in the environment this week and confirm upgrade to **3.16.3**, (2) audit the docker-compose.yml for any instance not yet upgraded and confirm the port 3001 bind address is **127.0.0.1 only** until upgrade is complete, (3) review the AgentDB learning store for any unexpected entries written before the patch was applied (the poisoning vector can be silent), (4) add the "MCP server bound to all interfaces by default" question to every agent-platform RFP, and (5) treat every MCP server as a tier-1 patch target with a documented authentication review before deployment.

### Microsoft Copilot for Word Worm: First Public Demonstration of Document-Borne AI-Worm Self-Propagation in a Mainstream Productivity Suite — 144 Days of Microsoft Coordination, No Robust Mitigation Available

**Håkon Måløy**, a Norwegian data scientist with a PhD in applied AI/ML, publicly disclosed on **July 29, 2026** (per coverage by **The Register**, **enklypesalt.com**, and references in **SC Media** and **Cybersecurity News**) a new class of **cross-domain prompt injection attack** that allows an **AI-worm to self-propagate through Microsoft Copilot for Word** by hiding malicious instructions in ordinary Word documents. Måløy worked with Microsoft from **March 2026** through public disclosure — **144 days of coordination** — and Microsoft ran two mitigation attempts (including a model upgrade) that did not close the broader class. "To my knowledge, this is among the first public demonstrations of document-borne AI-worm self-propagation through normal workflows in a mainstream commercial productivity suite," Måløy wrote. The structural argument: "Relying on the model to detect XPIAs therefore resembles asking an interpreter to execute an untrusted program to determine whether that program is safe to execute."

**The worm propagation chain.** Per Måløy's writeup (as reported by The Register), the attack uses a financial-report example. An employee downloads a market analysis from a trusted website that has been compromised; the document contains **hidden malicious instructions inserted as small white text**. When the employee uses the document in Copilot for Word, the hidden instructions tell Copilot to **alter figures in the report** the employee generates and to **copy the worm into any new documents** the employee creates. If another employee later adds that report to their own work, the whole process begins again, and documents generated from it also contain the worm. Per Måløy, "the attack can therefore continue without further involvement from either the compromised website or the original malicious document. The attacker does not need access to the victim's Microsoft 365 tenant. The attacker only needs to share a malicious document with the victim."

**The "LLMs all the way down" architectural argument.** Per Måløy's writeup, "For AI-assistants to be useful, they often must process emails, documents, webpages, memories, tool outputs, and other information that may be controlled by an attacker." The fundamental architectural problem: if the LLM has to process data in order to determine it contains an attack, the attack could already be influencing that determination. Måløy asserts that adding another model to detect malicious content only moves the problem outward: "a 'LLMs all the way down' scenario." The long-term challenge, Måløy argues, lies in designing systems in which goals and intentions also exist independently of the information being processed. Until that time, "any system that integrates an LLM into a trusted workflow today must assume that attacker-controlled content entering the model's context will result in compromise at some rate."

**The "no customer-side remediation" finding.** Per Måløy, "No customer-side remediation fully addresses the issue at the time of publication." The partial mitigations are: (1) treat externally sourced documents as untrusted when using them in Copilot, (2) fully review every document before sending it to Copilot, and (3) fully review any Copilot-generated or edited document before distributing it. Per Måløy, "if you're going to have to actually read that stuff, you might as well just cut Copilot out of the loop and do the thinking yourself." The framing is the same one the **Penligent five-category jailbreak taxonomy** (covered Jul 27) and the **GitHub GitLost: GitHub's AI Agent into Leaking Private Repos** disclosure (covered Jul 6, surfaced again in Noma Labs' Jul 29 coverage) make from different angles: indirect prompt injection is the new class of attack that survives every model upgrade, and the defense has to be at the system layer rather than the model layer.

**Why it matters:** First public demonstration of document-borne AI-worm self-propagation in a mainstream commercial productivity suite, with Microsoft unable to close the broader class after 144 days of coordination and a model upgrade. The procurement consequence is the same one the **Azure DevOps MCP confused-deputy** (covered Jul 28) and the **Hugging Face customer-controlled sandbox boundary** (covered Jul 29) make: every enterprise Copilot deployment now needs an explicit "what document sources are trusted" question, and the answer has to be in writing in the deployment runbook. For enterprise security teams: (1) audit the document source allowlist for every Copilot deployment in the environment, (2) treat every externally sourced document as untrusted by default and require human review before Copilot ingestion, (3) add the "document-borne worm" attack class to the standard data-loss-prevention checklist, and (4) require human review of every Copilot-generated financial document before distribution as a baseline control until Microsoft ships a robust mitigation.

### The RufRoot Attack Chain: How Zero-Authentication MCP Bridge Becomes a 233-Tool RCE Pipeline in a Self-Hosted AI Agent Platform

The **RufRoot** vulnerability (CVE-2026-59726) is the **first CVSS 10.0** in the MCP ecosystem, and the attack chain is structurally identical to the **JFrog Artifactory 8-CVE chain** (covered Jul 29) and the **Arista VeloCloud CVE-2026-16812** (covered Jul 29): a **default-allow configuration** on a management surface becomes the full attack surface. The chain unfolds in four stages. **Stage 1: MCP Bridge discovery.** The attacker scans for `POST /mcp` on port 3001. The default `ruflo/docker-compose.yml` binds the port to 0.0.0.0, so any network-reachable instance responds. **Stage 2: Tool inventory enumeration.** The attacker calls `tools/list` on the MCP Bridge and receives the full 233-tool inventory, including `ruflo__terminal_execute`, `ruflo__database_query`, `ruflo__agent_spawn`, and `ruflo__memory_write`. **Stage 3: Initial RCE via terminal_execute.** The attacker calls `ruflo__terminal_execute` with `command: "id && hostname"` and receives shell execution as the container's `node` user. The command blocklist (`AUTOPILOT_BLOCKED_PATTERNS`) does not apply to the `/mcp` endpoint. **Stage 4: Full compromise chain.** With shell access, the attacker reads provider API keys from the container environment, queries the MongoDB instance (also bound to all interfaces by default) for stored conversation history, spawns new agent swarms on the victim's keys, and writes to the AgentDB learning store to poison future agent outputs. The full chain executes in minutes, and the operational signal is the same one the **Hugging Face customer-controlled sandbox boundary** (covered Jul 29) and the **n8n fourth-sandbox-escape** (covered Jul 28) make: a single management surface becomes the full attack surface, and the procurement consequence is that every enterprise MCP-server deployment now needs an explicit "is the MCP server bound to all interfaces by default" question.

**The "MCP Bridge as central nervous system" architectural finding.** Per Noma, "The MCP Bridge isn't a random auxiliary debug interface; rather, it is Ruflo's central nervous system. Every tool call, every agent action, every memory operation goes through the MCP bridge. Mistakenly giving unauthenticated access to the MCP Bridge means giving unauthenticated access to everything." The architectural finding is the same one the **Hugging Face customer-controlled sandbox boundary** (covered Jul 29) and the **Azure DevOps MCP confused-deputy** (covered Jul 28) make from different angles: the agent platform's central orchestration layer is the attack surface, and the trust assumption (that the orchestration layer can be trusted) is the structural security boundary. The procurement consequence is the same one the **MCP 2026-07-28 final specification's OAuth-aligned authorization** (covered Jul 29) and the **CREST AI-Enabled Pentesting Accreditation** (covered Jul 28) make: every enterprise MCP-server deployment now needs an explicit "is the orchestration layer trust assumption enforced" question, and the answer has to be in writing.

**The "AgentDB poisoning as silent contamination" operational signal.** Per SecurityWeek, successful exploitation enables poisoning the AgentDB learning store to influence AI outputs for all users. The operational signal is the same one the **SourTrade browser-assembled malvertising** (covered Jul 27) and the **Trim AI Pentest Checker** (covered Jul 25) make from the offensive side: the attacker now has a write path to a learning store that other agents will read from, and the contamination is silent because the writes are normal user-facing operations from the platform's own perspective.
