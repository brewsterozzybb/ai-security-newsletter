## 1. Headliners

### AsyncAPI npm Supply Chain Attack: Compromised GitHub Actions Pipelines Push 92,000-Line Miasma Botnet to 2.25 Million Weekly Downloads

Attackers compromised **four core @asyncapi npm packages** on July 14 by exploiting misconfigured GitHub Actions workflows — not by stealing npm tokens or compromising maintainer accounts. The result is the most sophisticated npm supply chain attack of 2026: a **92,000-line modular malware framework** with command-and-control channels spanning HTTP, Nostr relays, Ethereum smart contracts, and a libp2p mesh network.

**How the pipeline was turned.** The attacker pushed commits under a placeholder git identity to two AsyncAPI GitHub repositories. Each repository's legitimate release workflow — trusted by npm via GitHub OIDC — published the malicious versions. The resulting packages carried **valid SLSA provenance attestations**, meaning they appeared to originate from an authorized workflow. The five trojanized packages were:

- `@asyncapi/generator` 3.3.1 (101k weekly downloads)
- `@asyncapi/generator-helpers` 1.1.1 (43k weekly downloads)
- `@asyncapi/generator-components` 0.7.1 (34k weekly downloads)
- `@asyncapi/specs` 6.11.2-alpha.1 and 6.11.2 (2.1 million weekly downloads)

**The three-stage payload.** The first stage is an obfuscated JavaScript statement that triggers a downloader when the infected file is imported at runtime. The second stage, retrieved from the IPFS peer-to-peer content delivery network, contains configuration and the main runtime — launched as a hidden process. The third stage, as documented by **Wiz**, is a 92,000-line malware framework with modular architecture, establishing persistence and communicating with C2 servers through multiple channels: HTTP, Nostr (a decentralized social media protocol), Ethereum smart contracts, and a libp2p mesh network. The campaign identifies itself as `miasma-train-p1`, and the payload is a descendant of the Miasma backdoor seen in previous supply chain attacks.

**Detection challenge.** Because the malicious commits used the legitimate project's own CI/CD pipeline, the resulting packages had valid provenance attestations. SLSA (Supply-chain Levels for Software Artifacts) attestations are designed to prove that a package came from a specific repository and workflow — but they do not verify that the workflow's inputs were safe. The attacker exploited the gap between "this package came from the right pipeline" and "this package is safe to install."

**Who caught it.** **Microsoft Threat Intelligence** identified the compromise on July 14 and published a detailed analysis. **StepSecurity** documented the CI/CD pipeline compromise mechanism, noting that the attacker used the same workflow configuration that the project maintained. **Socket** detected the first-stage implant within hours.

**Why it matters:** This attack proves that **SLSA provenance attestations are not a safety guarantee**. The attacker didn't need to steal tokens or impersonate a maintainer — they simply pushed code through the legitimate pipeline. For any organization that pulled `@asyncapi/specs` 6.11.2 or any of the other compromised versions in the window after July 14, the Miasma payload has already established persistence with its multi-channel C2 infrastructure. The implication for the npm ecosystem is that CI/CD pipeline security — not just package signing — is now the critical trust boundary.

## 2. Breaking News

### SonicWall SMA 1000 Zero-Days (CVE-2026-15409, CVSS 10.0): Unauthenticated SSRF Actively Exploited in Targeted Attacks — CISA Adds to KEV

SonicWall has confirmed active exploitation of **two zero-day vulnerabilities** in its Secure Mobile Access (SMA) 1000 series appliances, the enterprise VPN gateways used by healthcare, financial services, and large-scale organizations. **CISA added both to the Known Exploited Vulnerabilities catalog** on July 14, giving federal agencies until July 17 to patch.

**The vulnerabilities.** CVE-2026-15409 carries a **CVSS score of 10.0** — the maximum severity — as a server-side request forgery (SSRF) that a remote unauthenticated attacker can exploit to make the appliance send requests to unintended locations. The second vulnerability, CVE-2026-15410 (CVSS 7.2), is a post-authentication code injection in the Appliance Management Console (AMC) that enables arbitrary OS command execution as administrator.

**Rapid7's findings.** In a follow-up report published July 15, Rapid7's MDR team stated it observed "active, targeted zero-day exploitation of internet-facing SMA 1000-series appliances since at least late last month" — weeks before SonicWall's advisory. Rapid7's researchers discovered the zero-days and coordinated with SonicWall's PSIRT before publication.

**The indicators.** SonicWall published specific IoCs for detecting exploitation, including requests to `/__api__/login` or `/__api__/logout` returning HTTP 200, and suspicious `host` parameters in `/wsproxy` requests returning HTTP 101. Organizations that find these indicators are advised to re-image physical appliances, change all passwords, and reset TOTP tokens.

**Why it matters:** A CVSS 10.0 vulnerability on an internet-facing VPN appliance with confirmed active exploitation is as urgent as it gets. SonicWall SMA 1000 appliances sit at the network perimeter, handling authentication and access for enterprise remote users. The weeks-long window between initial exploitation (late June) and public disclosure (July 14) means attackers have had a head start.

Organizations running Azure OpenAI should verify that the patch has been applied to their instances. The broader pattern of exploding patch counts means the window between disclosure and exploitation is shrinking faster than ever.

### LegacyHive: Windows Zero-Day PoC Released Hours After Patch Tuesday — Functional on All Fully Patched Systems

Security researcher **Nightmare Eclipse** (aka Chaotic Eclipse) released a proof-of-concept exploit called **LegacyHive** on July 15 — just hours after Microsoft's Patch Tuesday — targeting a Windows User Profile Service (ProfSvc) arbitrary hive load elevation of privilege vulnerability. The PoC is functional on all supported desktop and server versions of Windows, including those running the latest July 2026 Patch Tuesday update.

**The details.** The PoC exploits ProfSvc, a core system component managing user accounts and environments. The publicly released version requires another standard user credential and a third username (which can be an administrator account), but the researcher noted that the original exploit did not require additional credentials and was not limited to the `usrclass.dat` hive. "Any hive could be loaded using this vulnerability," the researcher stated.

**The ongoing dispute.** Nightmare Eclipse and Microsoft have been locked in a heated dispute since at least April 2026, with the researcher releasing multiple exploit details before Microsoft could patch them. Three of the vulnerabilities in Microsoft Defender came under active exploitation shortly after public disclosure. The researcher also disclosed the RoguePlanet Defender vulnerability earlier this month.

**Why it matters:** The gap between Patch Tuesday and exploit publication is now measured in hours, not weeks. LegacyHive is not a complete exploit — it requires additional credentials in its published form — but it provides a starting point for attackers. For organizations still deploying July 2026 patches, the clock is already running.

## 3. Technical Deep Dives

### SEP-1763: The MCP Interceptor Framework — The Missing Primitive for Agent Security

**WorkOS** published a deep technical analysis of **SEP-1763**, the proposed Interceptor Framework for the Model Context Protocol, on July 14. The proposal, first filed in November 2025 and still marked Draft, has its own Working Group and dedicated charter — but almost nobody outside the working group has written about it. WorkOS's analysis changes that.

**The problem.** Platform teams running MCP servers across multiple environments need consistent PII redaction, audit logging, rate limiting, and prompt injection validation — applied the same way regardless of whether a server is written in Python, Go, or TypeScript. Currently, there is no standard way to do this. Every team either bolts middleware onto their own server or stands up a gateway that may not match what each server expects. The SEP's authors describe this as "an M times N problem": M clients each integrating with N different middleware approaches.

**What an interceptor is.** The proposal introduces interceptors as a new first-class MCP resource type, sitting alongside tools, prompts, and resources. Each interceptor declares:
- A name and version
- The events it subscribes to
- A type: validation, mutation, or observability
- A phase: request, response, or both
- A priority hint for ordering
- Optional protocol version compatibility
- Optional JSON schema for its own configuration

The events an interceptor can hook into span three categories: server features (`tools/list`, `tools/call`, `prompts/get`, `resources/read`), client features (`notifications/initialized`, `resources/subscribe`), and transport-level events (connection open, close, error).

**The real-world pattern.** What makes the analysis notable is that teams are already building production systems against this pattern before the SEP is accepted. Real-world implementations are shaping the proposal in real time. The pattern is the same one that made MCP tools work: discoverability plus a standard invocation pattern. Instead of M times N custom integrations, you get M plus N: clients implement the interceptor call pattern once, servers expose interceptors through one standard interface.

**Why it matters:** SEP-1763 is the most important unaccepted MCP proposal for security practitioners. If adopted, it would standardize how every MCP server handles cross-cutting security concerns — from prompt injection detection to credential validation to audit logging. The fact that teams are already building to this pattern means the security community is voting with its code, even before the spec is finalized. For organizations deploying MCP servers today, the interceptor pattern is a reference architecture worth implementing regardless of the SEP's formal status.

**Sources:** [WorkOS](https://workos.com/blog/mcp-interceptors) | [SEP-1763 on GitHub](https://github.com/modelcontextprotocol/modelcontextprotocol/issues/1763)

### Securing Agent-to-Agent (A2A) Communication: A Practical Guide to Multi-Agent Security Risks

A detailed security guide published July 16 by **Arnav Sharma** examines the security model of the **Agent-to-Agent (A2A) protocol** — Google's open standard for inter-agent communication, now stewarded by the Linux Foundation — and finds that the protocol's deliberate design choice to leave identity and authorization to implementers creates a fragmentation risk that is only now being addressed.

**How A2A works.** A2A defines how autonomous agents discover one another, negotiate capabilities, exchange tasks, and return results over HTTPS using JSON-RPC 2.0, with Server-Sent Events for streaming updates. Every A2A server publishes an "agent card" — a JSON document at a well-known path describing the agent's name, capabilities, supported skills, endpoint URL, and authentication schemes. The card drives four stages: discovery, task negotiation, task execution, and result return.

**The security gap.** Rather than inventing a new identity system, A2A aligns with existing OpenAPI authentication schemes and lets each agent declare what it supports. The protocol gives you the plumbing, not the guarantees. "Trust establishment, credential handling, and agent identity verification sit outside its scope by design," the guide notes. This means that any given A2A deployment's security posture depends entirely on what the implementers put in place.

**The specific attack vectors.** The guide identifies concrete risks:
- **Agent card spoofing:** An attacker publishes a fraudulent agent card impersonating a legitimate agent, redirecting task delegation to a malicious endpoint.
- **Cross-agent prompt injection:** A compromised agent sends crafted task descriptions to other agents, injecting instructions that the receiving agent's LLM processes as commands.
- **Credential chain compromise:** A single compromised agent exposes credentials that other agents in the mesh trust, creating a cascade failure.
- **Lack of audit trails:** Without standardized interceptor-style logging, reconstructing the chain of delegation across multiple agents is difficult.

**Why it matters:** As multi-agent deployments move from experimental to production, the A2A protocol's "bring your own identity" model means every organization's security posture is only as strong as its weakest agent implementation. The guide's recommendations — mutual TLS, OAuth 2.1 with PKCE, per-delegation consent, and standardized audit logging — mirror the same controls the MCP ecosystem is converging on. The convergence of MCP and A2A on the same security primitives suggests that the industry is starting to build a coherent security model for agentic architectures — even if neither protocol has fully shipped it yet.

**Sources:** [Arnav Sharma](https://arnav.au/2026/07/16/securing-agent-to-agent-a2a-communication/)

## 4. Community Pulse

### UN AI Scientific Panel Releases First Global Scientific Assessment: "AI Advancing Faster Than Governance Can Manage"

The **Independent International Scientific Panel on AI**, established by UN General Assembly Resolution A/RES/79/325 in August 2025, released its **Preliminary Report** on July 15 — the first global scientific body on AI publishing a consensus assessment of the technology's trajectory and risks.

**The finding.** The report's central conclusion is that artificial intelligence is advancing faster than current governance systems can manage. The panel, composed of independent international scientists, urges governments to strengthen AI governance frameworks, noting that the breakneck pace of machine learning advancement has outstripped the capacity of individual nation states to regulate or even comprehend the underlying systems.

**The scope.** The report covers the full spectrum of AI risk: from cybersecurity and data privacy to labor displacement, misinformation, and the concentration of AI compute power. It calls for international coordination on AI safety standards, testing regimes, and incident reporting — echoing many of the themes that the AI security community has been arguing for at the technical level, now elevated to a global scientific consensus.

**The cybersecurity angle.** The report specifically flags that AI systems are both a vector for new attacks (AI-generated exploits, prompt injection at scale) and a target for traditional attacks (supply chain compromise of AI infrastructure, model theft). It recommends that AI safety frameworks include cybersecurity testing as a mandatory component.

**Why it matters:** This is the first global scientific consensus document on AI risks. It establishes a baseline for international AI governance discussions that will shape everything from export controls to model registration requirements. For security practitioners, the report provides authoritative backing for arguments that AI security is not a niche concern but a global governance priority.

### Future of Life Institute Publishes Summer 2026 AI Safety Index — Benchmarks Leading AI Companies

The **Future of Life Institute** released its **Summer 2026 AI Safety Index** on July 15, rating leading AI companies across key safety and security domains. The index measures companies on military use of AI, safety research investment, transparency practices, and governance structures.

**The framework.** The index evaluates companies across multiple indicators, including the extent to which they develop or supply AI for military and defense applications, the strength of their safeguards governing those engagements, and their investment in safety research relative to capability development. The report notes that "military deployment raises the stakes of AI failures from commercial harm to loss of life and escalation risk, including the erosion of meaningful human control over the use of force."

**The context.** The index arrives as institutional benchmarking of AI safety practices becomes a key tool for procurement decisions, insurance underwriting, and regulatory compliance. The EU AI Act's August 2026 deadline for compliance is driving demand for documented, auditable safety practices — and the FLI index provides a framework for evaluating whether major AI vendors meet basic safety thresholds.

**Why it matters:** For security teams evaluating AI vendors, the FLI Safety Index provides a structured framework for assessing security and safety practices. The index's focus on military use, transparency, and governance is directly relevant to procurement decisions, especially for organizations in regulated industries or those with national security exposure.

## 6. Five Things to Take Into the Rest of the Day

1. **Treat npm packages with valid SLSA attestations as still suspicious.** The AsyncAPI attack proves that provenance attestations verify the pipeline, not the code. Any package published through a compromised CI/CD workflow will carry valid attestations. For any npm package pulled over the last 48 hours, verify the commit hash and the workflow that produced it — not just the attestation badge. The `@asyncapi/specs` package at 2.1 million weekly downloads was the highest-volume victim; check your lockfiles.

2. **Patch SonicWall SMA 1000 appliances immediately.** CVE-2026-15409 is a CVSS 10.0 unauthenticated SSRF with confirmed active exploitation since late June. CISA requires federal agencies to patch by July 17. If you are not a federal agency, the threat model is the same — attackers are already in the window. Apply the platform-hotfix versions (12.4.3-03453 or 12.5.0-02835) and check for the IoCs SonicWall published: `/__api__/login` requests returning HTTP 200, and suspicious `host` parameters in `/wsproxy` requests returning HTTP 101. If you find indicators, re-image the appliance.

3. **Verify Azure OpenAI instances are patched for CVE-2026-45499 (CVSS 9.9).** The elevation of privilege vulnerability in Azure OpenAI is Microsoft's cloud-hosted LLM service. If your organization uses Azure OpenAI for production AI workloads, confirm that the July 2026 updates have been applied. The vulnerability is critical (CVSS 9.9) and the patch was included in the record 622-vulnerability July release — but service-level updates may have been applied separately.

4. **Build MCP interceptor-style guardrails even before SEP-1763 is finalized.** The pattern of validation, mutation, and observability interceptors for MCP is already being built in production by teams who cannot wait for the spec to ship. The insight from WorkOS's analysis is that the interceptor pattern works regardless of protocol status: implement PII redaction, audit logging, rate limiting, and prompt injection validation as middleware layers on any MCP server you deploy. The MCP ecosystem is converging on this pattern — building it now means you are ahead of the standard, not behind it.

5. **Audit your A2A agent card exposure if you run multi-agent deployments.** The A2A security guide's core finding is that the protocol leaves identity and authorization to implementers. If you are running agents that use A2A for inter-agent communication, verify that your agent cards are not publicly discoverable, that mutual TLS or OAuth 2.1 with PKCE is in place, and that agent card spoofing would be detected. The protocol's "bring your own identity" design means your security posture is only as strong as your weakest agent.
