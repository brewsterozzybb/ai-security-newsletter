### n8n Fourth Sandbox Escape in 12 Months: Security Joes Bypasses CVE-2026-27577 Patch With Arrow-Function AST Gap + Reflect.get() Denylist Bypass — CVSS 8.7, n8n Process Privileges

**Security Joes** disclosed on **July 27, 2026** (per **The Hacker News** coverage) a new high-severity expression-sandbox escape in **n8n**, the most popular open-source workflow-automation platform, that lets an authenticated workflow editor execute operating-system commands on the n8n server as the n8n process. The vulnerability is tracked as **GHSA-gv7g-jm28-cr3m** with a **CVSS 4.0 score of 8.7**, affects versions **<2.31.5 and >=2.32.0, <2.32.1**, and is n8n's **fourth sandbox escape in 12 months** — following **CVE-2025-68613** (late 2025, ThisSanitizer bypass), **CVE-2026-25049** (February 2026, CVSS 9.9, destructuring bypass), and **CVE-2026-27577** (February 25, 2026, CVSS 9.4, SpreadElement bypass). The structural pattern — a patch, a new bypass, another patch, another bypass — is the operational signal every AI workflow platform is now generating, and the agent-era equivalent of the **ImageTragick (CVE-2016-3714)** decade-long chain of incomplete fixes.

**The two-condition exploit.** Per the Security Joes technical writeup, the bypass combines two unhandled conditions in n8n's expression sandbox rewriter (`VariablePolyfill.ts` and `expression-sandboxing.ts`): (1) the **ArrowFunctionExpression AST parent type** is treated as a no-op in the switch statement, so identifiers in arrow signatures or concise bodies are not polyfilled — `() => process` returns the real Node.js `process` object instead of the sandboxed value; (2) the property denylist (`getBuiltinModule`, `binding`, `dlopen`) is enforced via `visitMemberExpression`, which inspects static property names — but `Reflect.get(obj, 'getBuiltinModule')` passes a string argument rather than a property name, so the denylist never fires. The combined payload is `{{ ((R,p)=>R.get(p,'getBuiltinModule'))((()=>Reflect)(),(()=>process)())('child_process').execSync('id').toString() }}`. Per Security Joes, "Neither alone is sufficient. Neither was covered by tests."

**The n8n-sandbox-escape lineage.** Per the Security Joes writeup, n8n's expression-sandbox history is a chain of incomplete patches: **CVE-2025-68613** (late 2025) used `(function(){ return this })()` to leak the real Node.js process, patched with a `ThisSanitizer`; **CVE-2026-25049** (February 2026, CVSS 9.9) used template-literal destructuring `{ [\`constr${'uct'}o\`]: c }` to bypass the sanitizer; **CVE-2026-27577** (February 25, 2026, CVSS 9.4) used `{...process}` inside a SpreadElement to expose the real `process` global, patched with a `visitSpreadElement` hook. The new disclosure is the first one to combine a **syntax-tree-type gap** (ArrowFunctionExpression) with a **property-inspection gap** (Reflect.get with a string argument), and Security Joes' research team said of the two conditions: "Neither alone is sufficient. Neither was covered by tests." The procurement consequence is the same one the **ServiceNow CVE-2026-6875** and the **Langflow CVE-2026-0770** (both covered in the Jul 24/26 newsletters) make: the agent-platform surface is now producing one new CVE per month per major platform, and the cadence is structural.

**The n8n-process-privilege blast radius.** Per The Hacker News's coverage, a successful exploit executes commands with the privileges of the n8n process, and Security Joes' report notes that access could expose **N8N_ENCRYPTION_KEY** and allow decryption of credentials stored in n8n — opening paths to connected databases, internal services, and cloud endpoints. The n8n Cloud deployment status is unclear; the public advisory does not say whether the flaw was exploited before the fix. Security Joes had not observed exploitation in the wild when its report was prepared. The mitigation is to update to **2.31.5 or 2.32.1**, and to enforce the org-level "trust workflow editor" controls that the advisory describes as incomplete short-term mitigations.

**Why it matters:** Fourth sandbox escape in 12 months for the most popular open-source workflow-automation platform, and the first one to combine a syntax-tree-type gap with a property-inspection gap. The structural pattern — patch, new bypass, new patch, new bypass — is the agent-era equivalent of the ImageTragick chain, and the procurement consequence is the same one the **ServiceNow CVE-2026-6875** and the **Langflow CVE-2026-0770** make: every agent-workflow platform needs to be treated as a tier-1 patch target with a documented sandbox-escape history. For enterprise security teams: (1) update every n8n instance to 2.31.5 or 2.32.1 today, (2) audit n8n audit logs for the published IoC patterns (anonymous `execSync` invocations, `process.getBuiltinModule` calls, `Reflect.get` on n8n process objects), (3) rotate N8N_ENCRYPTION_KEY for any instance that ran a vulnerable version in the last 30 days, (4) treat n8n as a tier-1 patch target with a documented sandbox-escape history, and (5) add the "expression-sandbox escape" attack class to the standard agent-workflow audit checklist.

### Azure DevOps MCP Flaw: Hidden HTML Comments in PR Descriptions Hijack AI Coding Agents — Confused Deputy, No CVE, No Fix Yet, Microsoft "Spotlighting" Defense Incomplete

**Manifold Security** disclosed a critical vulnerability in **Microsoft's Azure DevOps MCP server** that lets an attacker with access to just one project **steer a victim's AI coding agent into stealing data from projects the attacker could never reach directly**, per **Cybersecurity News** coverage on **July 22-27, 2026**. The bug is a classic **indirect prompt injection via invisible HTML comment** combined with a **confused-deputy** privilege-escalation pattern, and the structural failure is the most operationally significant one of the week: Microsoft's own **"spotlighting"** defense — which wraps untrusted external content in delimiters so the model can distinguish data from instructions — was **not applied to the tool returning PR descriptions**, leaving exactly the entry point the attackers used. Microsoft acknowledged and triaged the bug via the **Microsoft Security Response Center**; as of publication, no CVE has been assigned, and no fix has shipped. The bug is the second MCP-server prompt-injection disclosure in 30 days, after the **AWS Kiro** MCP-config-rewrite chain (covered earlier in July).

**The hidden-comment indirect-prompt-injection chain.** Per Manifold Security's writeup, Azure DevOps PR descriptions support Markdown, so an attacker can embed instructions inside an **HTML comment** that renders as nothing in the web UI but is still returned verbatim by the API. When a victim asks their agent to review that PR, the agent ingests the hidden text and follows it as if it were a legitimate command. In the proof of concept, the injected comment instructed the victim's agent to (1) approve the PR, (2) trigger a pipeline in a completely different "Payments" project, (3) read a confidential wiki page there, and (4) post its contents back as a PR comment the attacker could see, all while telling the agent not to mention any of it to the human reviewer. Because the agent operates with the victim's own credentials, it could reach data the attacker had no direct access to. The chain is the textbook **confused deputy**: a privileged actor (the agent) is tricked into misusing its own authority on someone else behalf.

**The "spotlighting applied inconsistently" structural signal.** Per Manifold Security's analysis, Microsoft had already anticipated the indirect-prompt-injection class of risk. The Azure DevOps MCP server uses a defense called **"spotlighting,"** which wraps untrusted external content in delimiters so the model can distinguish data from instructions. The fix, introduced in **PR #1062**, was applied to the tools returning pipeline and wiki content — but **not to the tool returning PR descriptions**, leaving exactly the entry point attackers used. The structural signal: even when the platform vendor ships a defense for the prompt-injection class, the defense has to be applied uniformly across every tool that returns external content, and the missing-application case is the structural entry point. The procurement consequence is the same one the **AWS Kiro MCP-config-rewrite** (covered earlier in July) and the **MCP Tool Poisoning** analysis (covered in last week's roundup) make: every MCP-server tool that returns external content needs a documented prompt-injection defense, and the defense has to be in the threat model before the server ships, not added incrementally per tool.

**The "lethal trifecta" framing.** Per Manifold Security's writeup, the researchers tie the incident to **Simon Willison's "lethal trifecta" framework** for agentic risk: **(1) access to private data**, **(2) exposure to untrusted content**, and **(3) a channel to send data out**. Any AI agent combining all three — exactly what the Azure DevOps MCP server does — can be turned against its owner by a single piece of poisoned text. The Azure DevOps MCP server is the production case study: the agent has all three (private code data via wikis/PRs, untrusted content via PR descriptions from external contributors, and a channel to send data out via PR comments and pipeline triggers). The procurement consequence is the same one the **OpenAI Agents SDK guardrails** (covered in the Jul 25 newsletter) and the **Microsoft Agent Governance Toolkit** (covered in the Jul 22 newsletter) make: every agent-platform RFP now needs an explicit "how does the platform mitigate the lethal trifecta" question, and the answer has to specify which of the three legs is closed (input filtering, output filtering, or channel restriction).

**Why it matters:** Second MCP-server prompt-injection disclosure in 30 days, and the first one to document the "spotlighting defense applied inconsistently" structural failure. The bug is unfixed at publication, the chain is reproducible by any external PR contributor, and the confused-deputy privilege escalation is the textbook agent-era attack pattern. For enterprise security teams: (1) audit the Azure DevOps MCP server version and apply the patch as soon as Microsoft ships one, (2) restrict which contributors can open PRs against projects the agent reviews, (3) treat any PR description that contains HTML comments as untrusted by default, (4) add the "lethal trifecta mitigation" question to every agent-platform RFP, and (5) add the "spotlighting applied uniformly" question to every MCP-server audit.
