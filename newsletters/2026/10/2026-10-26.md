## 1) Wiz: "Gheist" plants secret-dumping workflows with stolen GitHub tokens, hunting AI-provider keys (AI-native: AI keys are named targets; vendor research)

**What changed:** [Wiz](https://www.wiz.io/blog/gheist-attempted-scaled-abuse-of-stolen-github-tokens-stumbles) (Sun 1:55 PM) has tracked Gheist since Sep 15. The tool (user agent `gheist`) commits a `sync-check` workflow to every repo a stolen token reaches. The workflow prints secrets into Actions logs, which are pulled via GitHub's API before the run is deleted, so "there is no attacker domain or outbound connection to block." Wiz recovered "more than 13,500 planted branches from more than 850 compromised accounts." A self-hosted-runner variant searches for 31 token formats, "including keys for AI providers such as Anthropic, Hugging Face, Groq and NVIDIA." Wiz calls that job buggy.

**The control gap:** since Jul 28, GitHub holds potentially malicious workflow runs in **public** repos until a collaborator approves, and every public Gheist run Wiz checked stayed blocked. "That hold doesn't apply to private repositories or GitHub Enterprise Server," where runs completed. In enterprise orgs, cloud credentials from the same org were later used to enumerate AWS Secrets Manager.

**Evidence type:** single-vendor telemetry; as of Oct 24 "ongoing and evolving." Token sources and actor are not established, and Wiz links it to no prior incident. **Action:** hunt for `ci-sync-*` branches and CloudTrail role assumptions from unexpected branches; scope OIDC trust to protected branches; rotate secrets wherever such a run completed.

## 2) Follow-up (Oct 23): PHP2Shell gets a public working exploit; Unit 42 retracts; still not on KEV (CVE main 1 of 3)

**What changed in window:**
- **Public PoC:** the "Steal My Bitcoin" [challenge](https://stealmybitcoin.com/) shows a win at 15:47Z Sun (11:47 AM) on a PHP 8.4.26 server. The [writeup and PoC](https://github.com/KillaBoi/StealMyBitcoin-PoC) (repo created 5:48 PM; [HN](https://news.ycombinator.com/item?id=50237379) 8:15 PM) is calibrated to Alpine's built-in CLI server. It says a Debian FPM build "will never match," and it succeeded in 7 of 10 lab runs.
- **Retraction:** [Unit 42](https://unit42.paloaltonetworks.com/cve-2026-109618-cve-2026-109619/) (page modified 5:46 PM; footer "Updated October 25… 2:15 p.m. PT") retracted its Oct 23 claim about a European government agency: "We are unable to confirm that initial access is associated with the specific PHP2Shell CVEs." THN also reported it Oct 25; its publish time is unconfirmed.
- **In-the-wild RCE, reported:** [BleepingComputer](https://www.bleepingcomputer.com/news/security/php2shell-security-flaws-now-sucessfully-exploited-in-the-wild/) (Mon 5:19 AM) relays honeypot evidence of confirmed RCE on Apache mod_php. Expel's Marcus Hutchins calls it "the highest quality confirmation… so far." The underlying honeypot report is dated Oct 24, in the gap (**background**).
- **Patch wave:** [Palo Alto](https://security.paloaltonetworks.com/CVE-2026-109618) (updated Oct 26, date-only) lists PAN-OS impact as availability only, with some hotfixes out and others due Oct 27–30. Oracle's [alert](https://www.oracle.com/security-alerts/alert-cve-2026-109618.html) (undated) covers Communications products and "will continue to be updated."

**Still open:** CVE-2026-115560 remains unpatched (mitigation `session.upload_progress.enabled=0`, per [Infosecurity](https://www.infosecurity-magazine.com/news/php-publishes-mitigation-advice/), 5:15 AM). **Not on KEV** as of ~8:27 AM despite the RCE reports. **Action:** patch PHP; track the vendor appliance fixes you run.
