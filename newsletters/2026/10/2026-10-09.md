## 1) Zenity says one prompt to a public AgentCore agent reached every agent in the account and region (AWS disputes it)

**What changed:** [Zenity Labs' overview](https://labs.zenity.io/post/agentcorruption-how-a-single-prompt-collapsed-the-entire-cloud-security-model) is stamped **Thu 8:58 AM** (26 minutes into the window); the [press release](https://zenity.io/press-release/zenity-labs-discloses-agentcorruption-a-chain-of-aws-agentcore-flaws) is date-only. Zenity says an agent tool that can make HTTP requests could reach the instance metadata service (IMDS); one prompt to an internet-facing agent returned its execution role's credentials, and that default role spanned all AgentCore agents in the account and region. The researchers say they could invoke internal agents, read conversations, pull secrets from Secrets Manager, and **plant malicious memories** that persistently altered agent behavior.

Per Zenity, AWS closed its Dec 25, 2025 report as "informative," and on Sep 29 Zenity saw AWS had removed permissions for "cross-region agent execution, reading private conversations, and accessing secrets stored in AWS Secrets Manager."

**AWS disputes it:** AWS told [TNW](https://thenextweb.com/news/aws-agentcore-zenity-agentcorruption-one-prompt-agents) (updated Thu 12:07 PM) the research "inaccurately paints expected and documented behavior as a vulnerability," and that "an agent can access resources in another AWS account only if the developer explicitly grants permissions on both the agent's execution role and the target resource." That concerns cross-account access; Zenity's claim is within one account and region, and the statement doesn't mention the default role or the Sep 29 change. TNW corrected its own headline, which had stated the claim as fact.

**Evidence type:** researcher experiment from an agent-security vendor, with video; dispute unresolved. **Limits:** no AWS bulletin or CVE found; the permission cuts are Zenity's observation, not an AWS announcement; needs a public chat path and an outbound-capable tool. **Action:** for clients on managed agent runtimes: can agent tools reach metadata endpoints, is each role scoped to its agent, and who can write memory?

## 3) PraisonAI and Pydantic AI: advisories where "sandbox" and "approval" controls did not bind (CVE-style main 1 of 2)

**What changed:** GitHub's reviewed feed shows 22 PraisonAI and 9 Pydantic AI advisories published Thu (12:36–6:01 PM). Highlights:
- **PraisonAI [GHSA-2xv2-w8cq-5gxw](https://github.com/advisories/GHSA-2xv2-w8cq-5gxw)** (CVE-2026-61447, critical, 10.0 as scored in the advisory): `CodeAgent` runs LLM-generated Python with the full parent environment "even when `CodeConfig(sandbox=True)`"; the flag is never checked, so prompt injection can leak environment secrets. Fixed in `praisonaiagents` 1.6.78.
- **PraisonAI [GHSA-29r9-67vg-qj56](https://github.com/advisories/GHSA-29r9-67vg-qj56)** (CVE-2026-60087, medium; also fixed in `praisonaiagents` 1.6.78): a tool's first approval is cached by name and reused with different arguments; the PoC approves a benign `write_file`, then writes `/etc/crontab` unprompted. Critical-tier tools (`execute_command`, `execute_code`) are exempt from the cache; `write_file` is not.
- **Pydantic AI [GHSA-h4xc-3qfq-jf93](https://github.com/advisories/GHSA-h4xc-3qfq-jf93)** (CVE-2026-107295, high, 7.6, 1:16 PM): the local chat UI (`clai web`) doesn't check Content-Type, so a website the developer visits can trigger the agent with their credentials. Localhost binding "does not prevent this," and `requires_approval=True` tools were unprotected "because the endpoint trusts approval decisions relayed by the client."

**Evidence type:** official repository advisories; we did not run the PoCs (the approval-cache PoC is a unit-level test); severities are author-set. No exploitation reported; not KEV. **Limits:** each needs the component deployed. **Action:** ask which agent frameworks clients run and whether approvals survive a changed argument.

## 4) Ollama CVE-2026-103663: unauthenticated `/api/pull` path traversal → root RCE on next restart (CVE-style main 2 of 2)

**What changed:** [CERT Polska](https://cert.pl/en/posts/2026/10/CVE-2026-103663/) (dated Oct 8, no time; NVD **Thu 10:16 AM**) says `digestToPath` doesn't validate layer digests, so an unauthenticated attacker can write a binary outside the model store; if the server can write `/usr/lib/ollama` ("the default in most Ollama Docker images"), it loads on the next restart as root. CVSS 4.0 9.4 from the CNA.

**Evidence type:** official advisory (CNA); no PoC or exploitation found; not KEV. **Limits:** needs a reachable server, writable library path and restart. **Fixed version unconfirmed:** the advisory says "fixed in version 0.35.0," but CERT's own table lists vulnerable versions "from 0.34.2 to 0.35.0," and we couldn't find the fix commit (releases through v0.40.2 exist). **Action:** inventory reachable instances and container permissions. Our inference, not the advisory's: until the fix is confirmed, don't expose `/api/pull` or give the server process write access to `/usr/lib/ollama`.

## Take into the day / Worth keeping

1. **Test the control, not the config.** A `sandbox=True` flag never read, an approval cached by tool name, an approval the client can set. **Use:** change the arguments after approval; try to read environment secrets from the "sandboxed" agent. **Source:** GitHub advisories, Oct 8. **Limits:** three advisories; the generalization is ours. **Tags:** `agent-guardrails`, `hitl-approval`.
2. **An agent runtime is a cloud workload.** **Use:** ask "if one public agent is compromised, what else can its credentials reach?" **Source:** Zenity, Oct 8; AWS via TNW. **Limits:** one platform; the permission fix is per Zenity; AWS disputes that it is a vulnerability. **Tags:** `agent-blast-radius`, `imds`.
3. **A hardening switch isn't proof the code path is gone.** **Use:** which IPC/ZMQ ports bind beyond loopback, and does disabling pickle remove it? **Source:** SGLang write-up (Oct 7) and CVE (Oct 8). **Limits:** one researcher's test, non-default layout. **Tags:** `ml-infra`, `deserialization`.
