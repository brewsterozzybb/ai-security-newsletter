## 1) GitLab critical patch: Duo agent prompt injection could run commands "attributed to other users," plus a CVSS 10 RCE (CVE-style main 1 of 1; AI-native)

**What changed:** GitLab's [patch release](https://docs.gitlab.com/releases/patches/patch-release-gitlab-19-4-2-released) (19.4.2/19.3.5/19.2.8, 24 CVEs) is dated Oct 12, no time, and 19.4.2 images were on Docker Hub by 1:00 AM Mon (pre-window). The in-window disclosure is the CVE records: GitLab published them **Mon 9:05 PM** (01:05Z Tue), followed by NVD (10:17 PM) and GitHub advisory mirrors (11:30 PM).
- **CVE-2026-96893** ([GHSA-5vgp-j37h-7wfx](https://github.com/advisories/GHSA-5vgp-j37h-7wfx), 7.3, EE 19.1+, Duo Agent Platform): an authenticated user could "inject specially crafted content into AI agent instructions, potentially causing unintended command execution attributed to other users." Needs victim interaction; found internally.
- **CVE-2026-97229** ([GHSA-9hj5-r43h-h3xg](https://github.com/advisories/GHSA-9hj5-r43h-h3xg), 10.0, CE/EE 19.2+): an "unauthenticated user [could] execute arbitrary code on the GitLab server via a specially crafted regular expression in a CI/CD configuration." GitLab doesn't explain how an unauthenticated user supplies CI configuration.

**Evidence type:** vendor advisory; no exploitation reported; not KEV; GitLab.com already patched. **Why it matters (our read):** if the agent's actions are logged as the victim's, the audit trail names the wrong person. **Action:** upgrade self-managed now; ask Duo users whether logs separate a user's own actions from agent actions.

## 2) Anthropic: small models "may be months away" from self-replicating on IoT devices (AI-native; lab research)

**What changed:** Anthropic's Frontier Red Team [post](https://www.anthropic.com/research/self-replicating-ai) is stamped **Mon 3:30 PM** (19:30Z). In Anthropic's tests:
- A 9B model got inference running on 8 of 9 hardware types.
- Gemma4-26B-A4B ran across 15 ~$55 Android TV boxes at 0.39 tokens/s.
- In a firewalled 8-node emulated-Android network over **unauthenticated ADB**, only GLM-5.2 replicated end to end.
- A capability trend line puts a ≤30B model there "by the end of 2026."
- Inherited notes raised Qwen3.5-9B's setup success from 45% to 61–84%.

**Limits (Anthropic's own):** a trivial exploit step makes results "an upper bound"; models deployed Llama3.1-8B, not themselves, and the worm's own model ran on a separate server, not on the nodes; the timeline extrapolates a proxy metric. **Evidence type:** lab experiment, not independently replicated; no such worm observed. **Our read:** Anthropic measured the capability a replicator needs and says no model small enough for these devices has it yet ("the floor and ceiling don't intersect"). The risk rests on poorly secured, internet-exposed embedded devices, the broad class also at issue in #3 (our analogy). Anthropic's suggested defenses include ISP flow monitoring for multi-GB weight transfers and Mirai-style quarantine.

## 3) France: refrigeration controllers hijacked at scale; CERT-FR adds Copeland and Dixell (general cyber; observed incident)

**Why a main without KEV/CVE:** CERT-FR-confirmed compromise at scale, with physical impact on internet-exposed, contractor-managed controllers (access vector unconfirmed), and campaigns "probably still under way": an emergency for retail, cold-chain, and facilities clients.

**What changed:** [CERTFR-2026-ALE-012](https://www.cert.ssi.gouv.fr/alerte/CERTFR-2026-ALE-012/) v1 (Oct 12) and v2 (Oct 13) are date-only; v2 text was in CERT-FR's RSS by 7:09 AM Tue (in window, our inference). It reports "nombreuses compromissions" of Danfoss AK-SM/AK-SC; v2 adds **Copeland xweb and Dixell xweb**. The attack, forcing continuous defrost, was Sunday night (pre-window). Danfoss told [Cooling Post](https://www.coolingpost.com/world-news/danfoss-moves-to-mitigate-cyberattack/) (**Mon 2:35 PM**) that most affected units were either end-of-life AK-SM800/AK-SC355 or current AK-SM800A units on outdated firmware. Store counts vary by outlet (Cooling Post: "around 500"); a Paris prosecutor is investigating.

**CERT-FR guidance:**
- Remove internet exposure, after checking insurance terms on the contractor data link.
- Verify defrost schedules.
- Restore access only via VPN; IP filtering is a stopgap.
- For EOL units left internet-exposed, a factory reset alone is "insuffisant": they will "certainement" be re-compromised.

**Unknowns:** CERT-FR names no access vector or CVE; attribution unknown. **Action:** sweep client attack surfaces for these controllers' web UIs and inventory contractor remote access.

## 4) Codex CLI daemon reportedly leaks env vars across sessions (AI-native; community report, not confirmed by OpenAI)

**What changed:** In [issue #53547](https://github.com/openai/codex/issues/53547) (**Tue 12:00 AM**; 0.162.1, macOS), a variable exported in one session (started with `--enable daemon_auto_start`) was visible to a second session that never set it: "somewhere between a bug and a security issue." Background: [#48195](https://github.com/openai/codex/issues/48195) (Sep 25) says that since 0.157.0 sessions auto-start a persistent, hourly self-updating daemon that "pins the environment of whichever session happened to start it"; its HN thread (Mon 2:29 PM, 576 pts) was the window's #2 story.

**Verified vs not:** issues read, not reproduced; the reporter enabled the flag explicitly, and we didn't confirm the 0.162.1 default; no OpenAI reply. **Why it matters (if confirmed):** a daemon that keeps the first session's environment, including any secrets, and self-updates outside the package manager would break secret isolation and provenance on developer fleets. **Workaround (from the issues; untested):** `daemon_auto_start=false`; `daemon stop` leaves the updater running.
